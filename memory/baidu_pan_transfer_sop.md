# 百度网盘分享转存 SOP

适用：用户丢一个 `pan.baidu.com/s/...` 分享链接，要求保存到我的网盘某目录。默认目标目录优先用用户明确给出的路径；未给路径时询问，或在用户授权下用默认资料目录。

## 触发与默认策略
- 触发输入：用户消息包含一个或多个百度网盘分享链接（`pan.baidu.com/s/`）且语义为保存/转存/搬运/核验；批量链接要逐链接串行处理、独立记录状态，单个链接失败不阻断其他链接。
- 保存路径：用户给路径则用用户路径；未给路径先询问“保存到哪里？”；若用户要求默认路径但尚未配置，建议默认 `我的网盘/编程百科/视频/AI/【出海】` 并请用户确认一次。
- 执行边界：每个链接先识别分享根/用户指定范围；若链接失效、提取码错误、分享根内容与用户要求明显不匹配、目标范围不清，先停下询问或标记该链接失败，禁止进入渐进式分批保存。
- 物理入口：优先使用已登录的用户浏览器页，通过 `web_execute_js` 复用 Cookie 调百度网盘 XHR；不要另起无登录态请求。
- 幂等要求：目标已有同名目录时进入目录补缺，禁止新建 `(1)`、`副本` 等重复树；每批保存后用 `api/list` 验证再继续。
## 入口判断
- 先用用户浏览器打开分享链接，保留登录态；如需提取码，优先从 URL `pwd=` 读取。
- 不要按截图/页面标题猜范围；保存范围以分享链接当前根目录为准。若 URL hash 带 `#list/path=...&parentPath=...`，仍需用接口确认真实根。
- 目标路径必须保持分享内层级：若分享根只有一个目录 `A`，保存到目标根后应是 `目标根/A/...`，不要把 `A` 内文件拍平。

## 关键接口
在分享页用 `web_execute_js` 调 XHR，取运行态参数：
- `window.yunData.bdstoken`
- `window.yunData.shareid`
- `window.yunData.share_uk`
- `sessionStorage.share_files_fsids` 可辅助识别根 fs_id

分享列表：
```js
GET https://pan.baidu.com/share/list
  ?is_from_web=true
  &uk=<share_uk>
  &shareid=<shareid>
  &order=name&desc=0&showempty=0&view_mode=1
  &web=1&page=<p>&num=<n>
  &root=1                         // 只用于分享真实根
  &dir=<encoded share path>        // 子目录用 dir，不要 root=1
  &bdstoken=<share bdstoken>
```

我的网盘列表：
```js
GET https://pan.baidu.com/api/list
  ?order=name&desc=0&showempty=0&web=1&page=<p>&num=<n>
  &dir=<encoded target path>
  &bdstoken=<mine bdstoken>
```

转存通常走页面已使用的 `share/transfer` XHR；先从 `performance.getEntriesByType('resource')` 或 DevTools/XHR 抓实际参数，再复用 cookie 登录态。不要臆造字段。

## 执行策略
1. 先 `root=1` 列分享真实根，记录顶层名称、`fs_id`、是否目录。
2. 确认目标根存在；不存在则用网盘新建目录接口或页面操作创建。
3. 默认保存粒度：小链接/小目录先一次性保存用户指定范围，不要无故拆批；只有遇到“转存数量超限/非会员限制/批量过大导致超时或失败”且已确认分享内容正确时，才进入渐进式分批。
   - 分批从粗到细：先按顶层目录/文件分批；仍超限再进目录按分页或更小 `fs_id` 批次；常用 `num=100` 拉列表。
   - 内容异常禁分批：链接失效、提取码错误、分享根不符、用户只指定部分但范围不清、父级列表本身异常时，不能通过减少批量“试着保存”，必须先询问或标记该链接失败。
   - 每批转存后立刻用 `api/list` 核对目标落盘，记录已完成 `fs_id/name`，重试只补缺，避免重复批次。
4. 已存在同名目录时不要重复创建同名副本；进入该目录继续补缺。

### 大包超限的自纠正 BFS 分批（实战：882 项整包 / 内含 git 仓库）
非会员单次 `share/transfer` 有数量上限（约 500），超限返回 `errno=12` 且 `info` 里子项 `errno=120`「转存文件数超限」。整包一次转必失败，需分批：
1. 顶层先逐个目录/文件分批转；某个目录整夹转仍超限（该夹内部就 >500，如一个 ~600 文件的 git 仓库），进入自纠正 BFS：
   - 对该目录：先尝试整夹 `fs_id` 一把转；成功（errno=0）即整棵子树原子落地，无需再下钻。
   - 整夹超限 → `share/list` 列它的直接子项，把**散文件**按 `chunk`（如每 400 个 fs_id 一批）转、**子目录**逐个整夹转。
   - 子目录整夹仍超限 → 在目标侧 `mkdir` 建同名镜像目录，递归下钻它再重复本流程。
2. 脚本化：把上面写成一个 `verify + 自纠正 BFS` 的单脚本后台发射（写 `window.__wlog/__wdone` 或 localStorage 记进度），跑完再核验。每个 transfer 记 `errno`，全 0 才算该节点完成。
3. **关键性质**：百度里 folder 转存 `errno=0` = 整棵子树原子拷贝。所以只要各层直接子项都 errno=0 落地，子树即完整，核验时无需再逐文件确认该子树。

### 增量转存（增补同步，默认口径）
适用：目标根/目标目录里已经存过这个分享（或它的旧版本），用户要求"去重/增量/只补新增"。核心是先 diff 再只转缺失，禁止整树重转产生副本。
1. 取两份清单：`share/list` 拉分享侧子项、`api/list` 拉目标同名目录子项，各记 `name/fs_id/isdir`。
2. 按 `server_filename` 求差：`missing = 分享侧 - 目标侧`（名字一致即视为已存）；`extra = 目标侧 - 分享侧`（一般是历史资源，不动）。
3. 只对 `missing` 的 `fs_id` 执行一次 `share/transfer`，`path` = 目标同名目录（不是目标根，避免层级错位）；`missing` 为空则直接报"已全部存在，无需转存"。
4. 转存后 `api/list` 复核目标目录 count/names，确认新增项落盘、无 `(1)/副本`。
5. **粒度声明红线**：默认只做"顶层子目录/文件名 diff"，名字匹配≠内部内容完整（旧文件夹里可能又有新增）。回报时必须写明本次去重粒度是"顶层名 diff"还是"逐层递归 diff"；用户要求严格完整时才逐层进同名目录递归比对再补缺，且如实说明代价。
（案例：2026-07-06 "5.Codex大合集教程" 分享18项 vs 账号已存16项，顶层 diff 出2个"7月更新"新目录，只转这2个 fs_id 到同名目录，复核18项无副本。）
（案例：2026-07-29 同一分享增至21项 vs 账号已存21项，顶层名字几乎全对齐（仅1个改名但内容逐层比对一致，不转）；顶层 diff 为空时不能停，逐层下钻进"0.7月最新更新【优先看】"子目录才发现分享侧多1个新文件（zip），只转这1个 fs_id 到该子目录，复核12项无副本。说明：改名/顶层对齐≠内容对齐，增量的新内容常藏在已存在的"最新更新"类目录里，必须进去比对文件级差集。）
5. 遇到分享接口 `errno=115` 等风控/违规不可列目录：先判定是不是缺参，不能直接跳过。
   - 参数排查顺序：抓页面原生 XHR/Fetch 或 Performance 记录；对比 `root=1`、父目录 `dir=<完整 /sharelink... 路径>`、子目录完整路径、短路径、`sekey/BDCLND`。若父目录能列出该条目但子目录完整路径仍 115，且页面正文也显示“没有数据/链接出错”，可判定为百度对子目录列表拦截，不是缺参数。
   - 防漏存兜底：父目录可见时必须保留该子目录条目的 `fs_id/path/name/isdir`，优先用父目录条目级 `fs_id` 执行 `share/transfer` 保存该目录本身；保存后以目标侧 `api/list` 递归核验落盘结果。禁止因子目录不可列就跳过。
   - 混合目录/文件场景：若目标侧显示该目录下同时有子目录和文件（如“2.Codex+ DeepSeek配置”目标侧为 2 个子目录 + 5 个文件），说明父级 `fs_id` 转存能落下混合内容；分享端深层列表 115 时无法用分享端证明内部全集，只能用父级条目存在、转存动作返回、目标侧清单作为证据。后续同类目录必须按“文件和目录都参与比对”的口径核验，不能只比对子目录。
   - 结论口径：若子目录分享端不可列，只能报告“父目录可见 + 已按父级 fs_id 转存 + 目标侧落盘清单/数量”，不能声称分享端深层复核通过。

## 核验闭环
- 顶层：分享真实根 vs 目标根下对应目录，名称/count 对齐。
- 中层：每个子目录至少核对一层名称差异：`missing = share - mine`，`extra = mine - share`。
- 大目录：全量比对超时时改分页摘要核验：总页数、末页 count、首页/末页首尾名称；必要时抽查关键页。
- 全树差集核验（用户要"没漏吧"、需决定性证据时）：逐层 BFS 收集两侧每个目录的子项名集合求差 `missing/extra`，统计两侧总 files/dirs。两侧 files 数、dirs 数、每层名集合全等且 `missing=[] extra=[]` 即 100% 完整。
  - **抗超时+抗并发导航**：`web_execute_js` 单次 return 有约 15s 窗口，全树 walk 必超时导致结果丢；浏览器被他人并发使用时，写入 `window.__x` 甚至 `localStorage` 的后台异步会被导航清掉。对策：把全树 walk 写成后台异步，**每下潜一层就把累计计数写回 `localStorage.__vf` 当心跳**（带 `ts`、`level`、错误进 `phase:'err'`），发射后用 `sleep + 读 localStorage` 分次轮询：看得到 level/count 在涨=存活，`phase:'done'` 取终值。心跳法比一次性 return 或纯后台变量都稳。
  - 若连全树 walk 心跳都被反复杀（浏览器持续被并发导航），退而求其次做**浅层结构核验**：只比两侧目标目录的直接子项名集合 + errno；因 folder 转存 errno=0 已保证子树原子完整，各层直接子项对齐即可判完整（比全树 walk 快且抗超时）。
- 注意目标根可能已有历史/其他资源；只比较本次分享根对应子树，不要把目标根额外项当成本分享 extra。
- 完成回复必须包含：保存路径、分享根识别结果、已核验范围、异常目录/errno、最终结论。批量链接还必须逐链接列出：链接序号/标题、状态（完成/跳过/失败/需用户确认）、保存子路径、核验摘要、失败原因或待确认问题。
- 若不是转存而是把百度网盘分享作为聊天/网页资源线索沉淀进知识库，必须保留原始分享 URL、提取码、来源消息、分享页可见标题、已读取范围和未读取边界；未下载/未转存/未读正文时，只能写成“资源线索/主题归类/待深读”，禁止写成课程正文摘要，也禁止只留标题不留链接。

## 已验证坑点
- 分享 URL hash 的 `path=/` + `parentPath=/sharelink...` 不等于 `share/list?dir=/` 可用；真实根应优先用 `root=1`。
- `share/list` 对 `/sharelink...` 顶层可能返回 `errno=2`，但深路径可用；不要据此误判缺失。
- 后台脚本可能 15s ACK 超时；拆小批、拆目录、拆分页继续，不要无信息重试。
- 数量口径易误判：分享页显示的总数（如"882"）常是**文件+目录合计**，不是纯文件数（本例真值 602 文件 + 274 目录 = 876）。核验时别拿"合计数"当"文件数"去追差，否则会误以为缺了几百个。用 diff（名集合比对）判完整比用总数判更可靠。
