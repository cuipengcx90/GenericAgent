# roi_monitor_sop —— ROI 日报任务关键前置与坑

来源：2026-09-23 本任务实测（只读取证 + 只读 v2 回测原型），零配置改动。

## 前置/用法
- 脚本：**仓根** `roi_monitor.py`（不是 temp/）；`python3 roi_monitor.py` = `pprint(run())`，会**写** `roi_history.json`（同日 `task_volume_v1` 快照幂等覆盖）。
- 口径：`task_volume_v1` = 扫 `sche_tasks/done/` **文件名**按日聚合，统计**全部**任务。
- 报告四段固定：dashboard / 趋势(7日·30日) / 异常告警 / 优化建议。

## 三个必知坑
1. **`avg_lines_per_task` 结构性死亡（不是"数据缺失"）**：`append_snapshot()`(约126–157行)**从不写**该字段，而 `detect_alerts()` 从**最新快照**取值 ⇒ 恒 `None` ⇒ **「平均产出 <100 行/任务」告警自 2026-06-26 起永不可能触发**（88 个快照中仅 1 个含该字段 = 2026-05-03 旧口径 115.7）。别照着旧报告说"自 09-19 为 null"——那是表层现象。
2. **阈值 100 与现行口径冲突 ⇒ 单修字段必误报**：100 源自 2026-05-03 的**代码产出口径**(115.7)；新口径=单次执行报告行数，实测**业务型 ~42.9 行/任务（中位 41）、心跳型 ~22 行（中位 20）**。所以"把字段补上"必须**同时重标定阈值**（分位数或 ~25 行），否则修复当天起永久误报。改源码需用户批准。
3. **全量口径跨期不可比（2026-09-21/22 断裂）**：心跳型任务（`folder_watcher`/`price_alert`/`bridge_autonomous`/`sqlite_snapshot`，无事件也照跑、报告短）历史占 **73.5%–87%**；随 09-21 归档 folder_watcher/bridge_autonomous、09-22 price_alert 转反射器，心跳量 ~50/日 **骤降至 1–2/日（占比 11–13%）**。⇒ 全量口径的 WoW 会出现**假象**：2026-09-23 报 **−10.5%**，而**业务型口径实为 +5.4%（vs30 +9.6%）**。**判读务必拆双口径**。

## 第四坑（2026-09-25 新发现）：指标计「执行次数」而非「任务种类」⇒ 同日多跑灌水
- 口径是扫**文件名**，同一任务当日重跑/补跑各留一份报告 ⇒ 计数虚高。实测近 7 日（报告数 / 不同任务数 = 灌水次数）：09-18 **60/15（45）**、09-19 24/8（16）、09-20 35/19（16）、09-21 **63/15（48）**、09-22 15/14（1）、09-23 12/12（0）、09-24 21/14（**7**，含 roi×3、birdie×3、haisou×3、weekly_inspection×2 的网络中断补跑）。
- 09-18/09-21 的灌水几乎全来自心跳型（price_alert×23-24、folder_watcher×23）⇒ 与坑 3 叠加：WoW 变化里混着「心跳被拉起几十次」+「补跑/重试」两个噪声源。**趋势判读须同时给去重任务种类数**。
- 例外：`zero_days`（<3 个/天）告警因计数虚高而更难触发（任务种类少但重跑多时会掩盖稀疏）。

## 回测基线（2026-09-25 实测，后续对比用）
- `temp/roi_backtest_v2.py`：评估 2026-04-23→09-25 共 **124 天，触发 44 天**，**全部**是「心跳占比 >85%」类；「业务层下滑」与「业务层任务稀疏」**0 次**触发；末次触发窗口 07-27→**08-07**（85.3–87.3%）。09-21/22 归档后占比降至 62.2% ⇒ **85% 阈值在现行结构下不会再触发（已过时）**。
- 2026-09-25 实测值：全量 mean7 **32.86** / 前7日 **56.0** ⇒ WoW **−41.3%**；mean30 39.93 ⇒ vs30 −17.7%；昨日(09-24) **21** 次（去重 14）；近30日 zero_days 空。业务型 n7 87（12.43/天）vs 前7日 79（11.29/天）⇒ **+10.1%**，行/任务 52.01 vs 36.24 ⇒ **+43.5%**；心跳型 n7 143 vs 313 ⇒ −54.3%；`hb_share7`=**62.2%**。
- `roi_history.json` **非 git 跟踪**（`git ls-files` 空，`git status` 亦不报）⇒ 收尾**无需提交**；快照总数 **90**（`task_volume_v1` 89 个、含 `avg_lines_per_task` 仅 1 个=2026-05-03 的 115.7）。
- 结论口径：本任务**无推送要求**，正常日只写快照 + 报告。

## 口径 v3（2026-09-29 R497 标定，未接线，待批）

**三条铁律**（全量口径只作旁证，判读一律用业务型）：
1. **心跳判定走单一源**：`tools/roi_task_class.json`（30 类任务；规则 = `per_active_day ≥ 1.0 ∧ median_lines ≤ 25`，规则违例 0；heartbeat = `folder_watcher`/`price_alert`/`bridge_autonomous`/`sqlite_snapshot`）。**禁止再散落文件名硬编码**。
2. **双口径并行**：全量 / 业务型 / 心跳型三行 + 心跳占比列；跨期比较只用业务型；同时给**去重任务种类数**（执行次数会被同日多跑灌水）。
3. **阈值须过「可触发性闸门」**：每条规则在历史评估窗内须 ≥1 次触发且 ≤33% 触发天数，否则视为死阈值（v2 的 `biz_drop>25` 仅 1/127、`bpd<4` 仅 2/127 即在 2026-06-05 后沉默）。

**v3 阈值（`tools/roi_thresholds_v3.json`，四条全 gate PASS）**：R1 `bpd < 4.0`（业务型执行量稀疏）/ R2 `lines7 < 26.6`（单任务均产出过低）/ R3 `biz_drop > 34.4`（业务层 7 日均 vs 30 日均）/ R4 `ratio > 5.85`（灌水比 = 执行次数 / 去重种类）；R5 `unclass7 > 0`（出现未登记任务名，fail-closed）。

**回测硬证据（127 天评估窗）**：`wow_all < -30` 触发 **20/127** 且末次连续至 **2026-09-28** —— 该触发在 09-21/22 心跳归档后已成**结构假象**（同期业务型 **+11.4%**）；v2 旧历史值 `V2a/V2b` 现场实测为 4/127 与 2/127（旧会话笔记的 `1/127` 口径不同，未采信）。

## 报告写法（避免重复踩坑）
- dashboard 同时给**全量 / 业务型 / 心跳型**三行；趋势表附**心跳占比**列；跨期比较只用业务型。
- 告警段必须显式写"字段缺失/阈值口径"这类**沉默盲区**，不能只抄脚本的 `alerts=[]`。
- 该任务**无推送要求**，不要额外发通知。
