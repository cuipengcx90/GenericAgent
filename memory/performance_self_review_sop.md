# 绩效考评 SOP（季度考评表：季初目标制定 + 季末自评填充）

适用：每季度填写「尚饮员工绩效考评表-崔朋-{年}-Q{n}.xlsx」。同一张表跨两个生命周期阶段：
- **季初**：制定 KPI 目标（B-G 列），见「季初目标制定」章节。
- **季末**：填员工自评（H/I + C15/C16），见「季末自评填充」章节及之后全部规范。
目标：目标 SMART 且承接业务重心；自评以**真实 git/产出物数据**为事实底座，措辞高大上不浮夸，结构严格对齐模板。两阶段共享下方「关键路径」「单元格结构红线」「已验证坑点」「工具」。

## 关键路径与对象
- 绩效表目录：`/Users/cuip/develop/文档/绩效/`
- 文件名规律：`绩效考评表-崔朋-{年}-Q{n}.xlsx`，唯一 sheet 名 = `模板`
- 数据源（git）：根 `/Users/cuip/develop/WorkSpaces/idea/smyze/bar-smyze/`，动态扫含 `.git` 子目录；author=`崔朋`，`--no-merges`，`--since/--until` **必带 `T00:00:00+08:00`**（裸日期丢当天 commit，致命级）。
- 数据源（产出物，量化亮点用）：`bar_smyze_opserver/docs`（设计文档库，统计 md 数/字数/业务域/模块数，证明架构设计主导）；`bar_smyze_opserver/.claude/skills`（自建 AI 研发 skill 数 + agents/hooks/commands，证明 AI coding 团队引领）。
- 季度区间：Q1=01-01~03-31，Q2=04-01~06-30，Q3=07-01~09-30，Q4=10-01~12-31（未结束季度用至今日）。

## 季初目标制定（阶段一，季度开始时填）
**填什么**：B7-B9（KPI 项名）、C7-C9（权重）、D/E/F 列（80/100/120 分三档标准）、G 列（数据来源）。A3 目标制定原则、F3 等级说明、A5/B5/C5/D5/H5/J5 表头**全是固定文案，勿动**。J/K 上级区、H/I 自评区季初留空（季末填）。

**KPI 项与权重（延续 Q2，除非业务重心调整）**：
| 行 | KPI 项（B 列） | 权重（C 列） |
|---|---|---|
| 7 | 自研点单平台 | 0.5 |
| 8 | 设备运维系统 | 0.3 |
| 9 | 日常团队配合度 | 0.2 |
权重合计必须 = 1.0（C12 公式 =SUM(C7:C11) 自动校验）。

**三档目标标准模板（D=80分 / E=100分 / F=120分，逐档递进）**：每个 KPI 项固定写 3 个维度，档间只调数值，措辞保持平行。
- 维度1 稳定性治理：`{系统}线上稳定性治理 80% / 95% / 110%`
- 维度2 迭代交付：`{系统}二期迭代需求交付准时率 80% / 95% / 110%`
- 维度3 缺陷量：`线上缺陷量 1个/人周` → `低于0.5个/人周且无重大缺陷` → `低于0.3个/人周且无重大缺陷`
- 协作域（第9行）三维度换成：跨团队协作响应及时率 / 任务进度与风险同步准时率 / 上下游协作满意度，同样 80%/95%/110%。
- G 列数据来源：填评判方（Q2 用「测试、产品」），保持简洁。

**GA 起草流程（用户已授权：参考上季 + 当前趋势起草初稿，用户再改）**：
1. 读上一季度表的目标区（B/C/D/E/F/G），作为结构与措辞基线。
2. 扫当前 git 区间（季初通常取上季末至今）+ docs/.claude 增量，判断业务重心是否变化（如某系统 commit 量骤增/新业务域上线），据此微调 KPI 项或权重，并向用户说明调整理由。
3. 套用上方三档模板生成 D/E/F 初稿，数值默认延续 80/95/110，无特殊依据不擅自抬高基线。
4. openpyxl 写入 B/C/D/E/F/G（**不碰 H/I/J/K 及 A3/F3 表头**）→ 保存 → 重载校验 C12 权重合计=1.0、公式未破坏。
5. 交付初稿摘要，列出"延续项 vs 本季调整项"，等用户拍板。

**目标制定红线**：①符合 SMART（可衡量、有数值、有时限）②权重合计=1.0 ③三档必须递进不可倒挂 ④不动 A3/F3/表头与上级区 ⑤季初不填任何自评/评分。

## 评分档位（来自 F3 说明）
S 116-120 / A 110-115 / B 96-109 / C+ 80-95 / C <80。
自评取 110-120 区间（A~S）；按域真实把握做区分度，**不要全给满分**（如主战场 120、投入较少域 115、定性协作 110）。

## 内容写作规范（措辞高大上 + 事实底座）
1. **先取数后下笔**：按 KPI 域把仓库分组，统计 commit 数/feat/fix，作为叙事底座，但 **I 列描述里不暴露 commit 原始数字**（用「100% 准时交付」「无重大线上事故」「多起高优隐患根治」等业务语言）。
2. **开发期 fix ≠ 线上缺陷**：git 的 fix commit 是开发期修复，严禁当线上缺陷量上报；线上质量用「无重大线上事故/线上缺陷低于目标阈值」叙事。
3. I 列每项结构：开头一句总评（含准时率/稳定性结论）+ 2-4 个小标题段落（如「线上稳定性治理」「迭代交付」「质量度量」），每段落对应真实业务成果。
4. C15/C16 各写 3 个带小标题的方面，**跨季度禁止照搬措辞**——延续结构可以，文字必须换口味（同义重构、换视角）。
5. 高大上词库参考：战略转段、体系化闭环、防火胜于救火、多层兜底、口径对齐、可观测性、技术债治理、可传承资产、协同演进。
6. **硬数字锚点（commit 数 ≠ 量化）**：定性叙述要配产出物事实数字才有说服力。可用的真实锚点：设计文档数（如 640+ 份）、业务域数（11）、功能模块数（57）、自建 AI skill 数（42）、交付准时率 100%、季度零重大线上事故。「十余/数十」一律升级为精确数字。
7. **动词去重**：避免「主导/建立/沉淀/推动/作为……核心」高频堆叠，单段同一动词≤1 次。替换库：确立、收敛、固化、牵头、抽象、交付、定义、根治、打通。写完用 `t.count("主导")` 等自检。
8. **核心亮点标签（崔朋专属定位）**：每季必凸显两张王牌——①架构设计主导（证据=docs 设计文档库）②AI Coding 团队引领（证据=.claude/skills 体系）。这两项放 I7 前列 + C15 第 1/2 项置顶。
9. **C16 改善项三条红线**：①禁 QA/执行岗调性（如「自动化测试与回归保障」会拉低层级，不可用）②禁正确的废话/口号（如「加强团队能力梯队建设」太虚）③必须有具体抓手、一看就知指哪件事。匹配「架构主导 + AI 引领」身份的优质改善项：设计文档与代码实现的同步维护、AI 生成代码的人工把关深度、运维系统的实质性体系化投入、稳定性治理的主动预警前移。改善方向应是「更高维还能更好」，不是「基础执行有缺口」。
10. **价值数据取舍**：涉及团队复用率/效率提升/新人上手周期等组织级结果数据，git 取不到、不易举证时**不写**（用户已确认稳妥优先），只用产出物可举证的硬数字。

## 跨期对账（季度间复用必做）
- 打开上一季度自评，逐条核对：上季 C16「需改善」的每一条，本季是否已有改善证据或仍延续？延续则换新角度表述，已改善则可在 C15 体现。
- KPI 域可能调整（Q1 偏建设、Q2 偏稳定性治理+迭代）：先读本季 B 列目标，按目标域重新归类仓库，不要套用上季域划分。

## 已验证坑点
- 表只有一个 sheet 名「模板」；`data_only=True` 读不到（无缓存值），必须 `data_only=False` 读公式/原始值。
- 单元格样式 wrap_text=True、vertical=center；填多行文本用 `\n` 换行即可，样式自动继承。
- I 列/C 列均为合并单元格，写入左上角坐标（I7/C15/C16）即可。
- 保存前确认 J 列上级评分占位（通常 100），勿覆盖。
