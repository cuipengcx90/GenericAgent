## 3. 每源「窗口长度」= 可复跑（验收③）

窗口用**两条互相独立的路径**测，数字完全一致（互为交叉验证）。

### 路径 A：快照内 `window --json`（在冻结副本上跑）

```
chrome/2026-09-25  visits 全表  → [30403, "2026-06-27 23:13:07", "2026-09-25 22:18:28"]
chrome/2026-09-25  urls 全表    → [11983]

kc/2026-09-25      /app/usage 流 → [25, "2026-09-01", "2026-09-25"]
```

### 路径 B：**源库副本**（连 `-wal/-shm`）+ `file:...?mode=ro`（验收③原文要求）

```bash
# 通用配方（★必带侧车，缺 -wal 会"假空"）
D=$(mktemp -d); cp "<src.db>" "$D/db"
for s in -wal -shm -journal; do [ -e "<src.db>$s" ] && cp "<src.db>$s" "$D/db$s"; done
sqlite3 "file:$D/db?mode=ro" "<SQL>"
```

| 源 | SQL | 结果 |
|---|---|---|
| Chrome `…/Google/Chrome/Default/History` | `select count(*), datetime(min(visit_time)/1000000.0-11644473600,'unixepoch','localtime'), datetime(max(visit_time)/1000000.0-11644473600,'unixepoch','localtime') from visits` | `30403 | 2026-06-27 23:13:07 | 2026-09-25 22:18:28` |
| 同上 | `select count(*) from urls` | `11983` |
| kc `…/Knowledge/knowledgeC.db` | `select count(*), min(date(ZSTARTDATE+978307200,'unixepoch','localtime')), max(date(ZSTARTDATE+978307200,'unixepoch','localtime')) from ZOBJECT` | `18145 | 2024-12-27 | 2026-09-25` |
| 同上 | 同式 + `where ZSTREAMNAME='/app/usage'`（另取 `count(distinct date(...))`） | `25 天 | 2026-09-01 | 2026-09-25` |

**窗口结论**：

- **Chrome**：`visits` 最老 = 今天往前整 **90 天**（2026-06-27）⇒ 90 天滚动，**超窗即永久删除**。
- **kc**：整库跨度 2024-12-27 起（含少量永久保留行），但 `/app/usage` 流只有 **25 个不同日期（09-01~09-25）**⇒ 该流按 **~23–25 天**滚动删除，这才是它的真实窗口（与既有记忆「≈4 周滚动 / 33 个不同日期」一致，因整库还含其它流）。
- 两源**均为每日不可逆丢数据**，故「每日一份」是唯一补救手段。

## 5. 只读自证（验收⑤）

- manifest 的 `src_before` / `src_after` 逐文件 sha256 对比，`src_verdict = unchanged`；本次 Chrome 侧同时登记了 `db` 与 `-journal` 两个文件（journal 也 unchanged）。
- **收尾复核**（本报告写作时重跑）：源库当前 sha256 仍等于 `src_after` ⇒ `相同? True`；源库 mtime = `2026-09-25 22:18:38`（早于本轮写入，未被触碰）。
- **边界（必须声明）**：验收设想的「源库上跑 `DELETE FROM … WHERE 0` 只读探针」在 Chrome 上**不可得**——热 journal 活库上的只读连接会阻塞到子进程被强杀（实测 `probe_sql` 记录：`★源探针不可得：子进程超时 >10s（已强杀）`）。故只读性以**三重替代证据**成立：
  1. 源库 + 侧车 sha256 前后逐字节一致；
  2. 在**冻结副本**上重跑同一条采集路径，副本 sha256 不变（`readonly_selfproof`）；
  3. 代码层只读白名单源文件、全程 `mode=ro`（探针在可写/只读两种连接上的正负对照已由 `T4` 自测覆盖）。
- 全程未改动任何源库、未写入 `memory/`。

## 7. 本轮踩到的新坑（已修）

- **★Chrome 热 journal ⇒ `sqlite3` backup API 在只读连接上永久阻塞**（实测残留 0 字节副本、整轮被工具超时强杀）。修法：`backup` 改为**子进程 + 硬超时**，超时即回退到「**raw 拷贝（db + 全部侧车）→ 副本回滚取一致性（`quick_check=ok`）→ `VACUUM INTO` 干净单文件**」；实测文件级拷贝 **0.0s**、`quick_check=ok`。
- **raw 拷贝必带侧车**（`-journal/-wal/-shm`），否则出现「假空」。
- 工具的**自证子调用用 5s 短超时**，避免只读探针把工具自身挂死（本轮即因此留过一次 0 字节残留，已清理 `/var/folders/.../T/rss-*`）。
