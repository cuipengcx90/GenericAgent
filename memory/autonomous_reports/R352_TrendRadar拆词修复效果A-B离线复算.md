## 1. 方法与数据（可复跑）

- **数据源**（全部本机只读）：
  - 每日新闻库 `~/projects/TrendRadar/output/news/<date>.db` → `SELECT title, platform_id FROM news_items`，只读 URI 打开；
  - 生产关键词：`ast` 解析 `sche_tasks/run_trendradar_digest.py` 的 `KEYWORDS` **字面量**（不 import，避免副作用）；
  - 当日供给：`GA/output/trendradar_morning|evening_<date>.material.json` 的 `rss.data` 标题。
- **四个臂**（对同一批历史日期重放检索）：

| 臂 | 语义 | 来源 |
|---|---|---|
| A 整串 | `query.lower() in title.lower()` | = TrendRadar `keyword` 模式现状（R343 确证的 0 命中根因） |
| B 逐词 | query 按空白拆词，任一 token 命中即算命中 | R343 修法A |
| B′ 词边界 | 同 B，但纯 ASCII 词按 `(?<![A-Za-z0-9])tok(?![A-Za-z0-9])` 匹配 | 本报告新增，量化子串误召回 |
| F 模糊 | 复刻 `SearchTools._fuzzy_match`（包含 → 1.0；`SequenceMatcher.ratio ≥ th`；否则关键词重合 ≥0.5） | R343 修法B |

- **计数口径**：`pair` = 同一标题在不同平台各算一次（= TrendRadar `_search_titles` 真实返回、= R343 impact 口径）；`title` = 同题跨平台去重（= GA 侧落地后的口径）。两者都给出。
- **区间**：2026-08-24 ~ **2026-09-21**（29 个已封盘日）。**当日 09-22 被剔除**——该库仍在写，半小时内条数即变，纳入会污染对账（见 §3）。

## 3. 与 R343 口径的对账（验收②）

R343 报告写的是「30 天 1396 条」，本次复算默认口径是 1400（30 天）。逐 (日,query) 差异共 15 处，**全部定位清楚**：

- **14 处（合计 −21）**：R343 按 (title, platform) 计数（未去重跨平台同题），本次默认按标题去重 ⇒ 我略低。改用 `--pair-mode` 后**逐日逐 query 完全一致**。
- **1 处（+30，全在 2026-09-22）**：该日数据库**仍在写入**（同一份库两次读取条数不同），R343 采样更早。剔除此日后：

| 区间 | 本工具 `--pair-mode` | R343 impact 同区间 | 差 |
|---|---|---|---|
| 08-24 ~ 09-21（29 天） | **1384** | **1384** | **0** |

⇒ 结论：两套复算**口径已完全对齐**，R343 的 1396 只是"含当日半成品日 + 未去重"的合成值，非误差。

## 4. 增量维度（本次新增，驱动决策的部分）

1. **`limit=30` 会吃掉 13.2%**：29 天里有 **17 次 (query·天) 命中数 ≥30**（触顶），按现状 limit=30 截断共**丢 180 条**（1384 → 约 1204）。且 `_search_titles` 的结果顺序是**平台遍历序 + 标题插入序**，不是热度序 ⇒ 被截掉的不是"最不重要的"，而是**任意**的。**只改 match 不改 limit = 信息被随机砍掉一成**。
2. **与 RSS 供给几乎不重合（去重价值关键）**：29 天里命中标题仅 **1 条**同时出现在当日 `material.rss`（400 条 RSS 供给）中 ⇒ **净新增 1253 条（99.9%）**。平台热榜与 RSS 是两条独立情报面，不是重复投喂。
3. **精度：子串匹配有 8.5% 误召回**：ASCII 词加词边界后 1283 → 1174（**少 109 条**），典型误召回如「如何评价美国海军最新公开的 **AIM-424**『恶意』远程空空导弹」（命中的是 `AI` 子串）。另有 68.4% 的命中**只靠泛词**（`AI`/`开源`/`编程`），抽样看多数仍是正当 AI 行业新闻（阿里 800 亿港元配售投 AI、Claude Code 退订、AI 眼镜隐私），但也有娱乐向条目（明星 AI 合成照、AI 续作动画）⇒ **建议 ASCII 词加词边界 + 保留人工/LLM 筛选**，不要在检索层再收窄（否则会误杀「AIGC」这类正当词）。
4. **成本可忽略**：命中标题平均 **25.5 字**，29 天累计正文增量 32,017 字 ≈ **1.1k 字/天**（约 400 token/天）⇒ 相对于现在报告 prompt 的量级属噪声级成本。
5. **修法B（fuzzy）不解决问题**：整体 query 与短标题的 `SequenceMatcher.ratio` 天然很低，th=0.3 只召回 58 条（拆词的 1/22），th=0.6 直接 0 条；且 0.3 档会纳入"整句相似"的偶然匹配。**若要在 TrendRadar 侧改，应改 `keyword` 模式为"多词 OR + 词边界"，而非启用 fuzzy。**

## 5. 判定（验收③）

> **批修法A，条件式批准**：拆词并集能让平台检索通道从 **0 条/天** 变成 **44 条/天**（29 天 1283 条），其中 **99.9% 不与 RSS 重合**，成本约 400 token/天、代码约 10 行；**但必须同批把 `limit` 从 30 提到 ≥80**（否则 17/29 天触顶、丢 180 条 = 13.2%），并给 ASCII 词加词边界（消 8.5% 误召回）。**不批修法B（fuzzy）**。

## 6. 落地建议（**只建议，未改任何配置**）

GA 侧（`sche_tasks/run_trendradar_digest.py`，约 10 行）：

```python
# _fetch_material_once 内：每个 KEYWORDS 由 1 次整串查询 → 逐词多次查询后并集
seen, hits = set(), []
for query in KEYWORDS:
    for tok in dict.fromkeys(query.split()):        # 去重保序
        res = _mcp_call(s, hdr, 'search_news', dict(
            query=tok, search_mode='keyword',
            date_range='今天', limit=80,            # ← 必须 ≥80（触顶实测最高 74）
            include_url=False, include_rss=False))
        for it in (parsed.get('results') or []):
            k = (it.get('title'), it.get('platform'))
            if k in seen:
                continue
            seen.add(k)
            hits.append(it)
```

TrendRadar 侧（可选、更彻底）：把 `_search_by_keyword_mode` 的 `query_lower in title.lower()` 改为多词 OR + ASCII 词边界，并在返回前按 `rank` 排序，让 `limit` 截断截掉的是冷门条目而不是随机条目。

## 7. 未验证 / 残余风险

- **未做真实 MCP 调用**：全部结论来自本机 DB 重放。真实链路还要验证 ①`search_news` 逐词调用的次数/耗时（16 词 × 2 query = 32 次调用/期，需确认 MCP 无速率限制）②返回顺序确实为平台遍历序（本报告按源码推断，未实调验证）。

- **历史可比性**：DB 里 157 天数据，但早期日期平台覆盖不同（如 08-24 为 1130 标题 vs 09-10 为 1371），跨月比较增量时需按 `titles` 归一。
