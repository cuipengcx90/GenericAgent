## 3. 新工具：`tools/doc_state_render.py`

`tools/doc_state_render.py`（392 行 / 17007 B / sha256 前16 = `2eb6a66cbaac73c2`）：

| 动作 | 语义 | rc |
|---|---|---|
| （默认）`--check` | 逐字节比对「生成块」与「从唯一源渲染的结果」 | 0 一致 / 1 DRIFT / 2 结构级（MISSING_DOC、SENTINEL_BROKEN、BLOCKED） |
| `--write` | 只改 `TARGETS` 里登记的**生成块**（哨兵之间）；块缺失时才在登记的插入点插入 | 0 复检一致 / 非 0 复检仍有问题 |

| `--json` / `--quiet` / `--docs A B` | 机器可读输出 / 静默 / 只针对点名文档 | — |

- 登记面 `TARGETS`：目前 1 条 = `docs/product/ROOT_MAP.md` 的 `stage-status` 块。**未登记的文档一律不碰**。
- fail-closed（结构级 rc=2，不误判成 DRIFT）：源文件不存在 / 源行数不足 / 锚点行缺失。
- 比对口径：生成块内文字必须**逐字节**等于渲染结果（渲染幂等 ⇒ 跑两次逐字节一致）。

## 6.1 顺带修复：`a4_drill.sh` 忽略 `PYTHON` 传入（仓内真缺陷）

**现象**（本次首轮全仓跑，日志 `/tmp/r478_run_tests_first.log`）：

```
=== tools/drill_suite.sh (免依赖演练) ===
  ❌ a4: /opt/homebrew/opt/python@3.13/bin/python3.13: No module named pytest FAIL: 判据单测未过 NG: 见上面 FAIL
drills: 7 passed, 1 failed
  FAIL drill_suite
suites run: 29
SOME SUITES FAILED
```

**根因链**：`run_tests.sh:169` 以 `PYTHON="$PY"` 调用 `tools/drill_suite.sh`；后者 `tools/drill_suite.sh:60` 再把 `PYTHON` 传给每个演练脚本；唯独 `control-plane/autonomy_v0/examples/a4_drill.sh` 用**裸 `python3`**，命中的是 PATH 首位的 homebrew `python@3.13`（无常装的 pytest）。这是**环境依赖型隐藏缺陷**：只有当 PATH 首位解释器缺 pytest 时才暴露，与本次文档门禁改动无关。

**修法**（`a4_drill.sh`）：改为 `PY="${PYTHON:-python3}"` 并统一用 `$PY`，判据失败时追加一行提示指明可用 `PYTHON=` 指定解释器。

**三点验证**（同一 shell，`PATH` 首位固定为 `/opt/homebrew/bin`）：

| 组 | 条件 | 结果 |
|---|---|---|
| A | `PYTHON=/opt/anaconda3/bin/python3` | 通过（rc=0） |
| B | 不传 `PYTHON`（负控：默认语义不该被改动引入） | 仍失败，且输出新提示行 ⇒ 修复未改变"裸 python3"时的既有行为 |
| C | 默认 PATH | 通过 |
| D | `bash tools/drill_suite.sh` 全量 | `drills: 8 passed, 0 failed` |

修复后以同一环境（A 组条件）复跑全仓 = §6 的 29 套件全绿。

**残余**：调用方若既不传 `PYTHON`、PATH 首位又是无 pytest 的解释器，drill 仍失败——这与 `run_tests.sh` 既有约定一致（脚本头部注释早已写明 `PYTHON=/path/to/python3 bash run_tests.sh`），本轮只修"诚实传参被忽略"这一处不一致，未改解释器选择策略。

## 7. 边界与残余（未关闭）

- **§5 后半未做**：散文里的状态陈述仍不可机械校验（实测：正则匹配「阶段N + 标记」7 条命中全是误报，见 `doc_state_check.py` 文件头）；生成块目前**只覆盖阶段三态**，FUTURE §5「设计」里点名的**批次状态 / 验收通过数 / 套件数 / 用例数**尚未纳入（那需要先有稳定的数据源，属下一步）。
- **校验入口的形态与 §5 设计不同**：设计写的是「`doc_state_check.py --strict` 同时检查生成块与唯一源一致」，实现落在**独立工具 + `run_tests.sh` 两行**。取舍理由：这两个门禁的失败语义不同（一个管标记、一个管生成块），合进一个 `--strict` 会让两边的负控互相耦合、也很难各自演化；本轮选择不改 `doc_state_check.py` 的判定语义（只订正它的文案）。**这是一处有意的偏差，不是遗漏**；若后续要坚持单一入口，可作为下一步合并（需同时迁移两边的负控）。
- **漂移闸门 `derive_guard` 不纳管 `ROOT_MAP.md`**（实测确认），因此本块不参与派生索引盖章；反过来，`ROOT_MAP.md` 的改动不会触发 `RESYNC`。
