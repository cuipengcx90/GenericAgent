## 2. `.lock` 归因定论（本轮新增的机制层结论）

### 2.1 事实链

- **文件级 `lsof` 命中 7 行**（6 个 uv 进程 + 1 个表头），全部指向同一个 inode `252820895` = `/Users/cuip/.cache/uv/.lock`：

```
uv  3046/10815/11523/34773/34952/42617 cuip  9u  REG 1,18 0 252820895 /Users/cuip/.cache/uv/.lock
```

- **`lsof <目录>` 返回 0 行** ⇒ 这正是 R370 得到「无持有者」的原因：`lsof` 传目录不会展开到「目录内被打开的文件」，会静默给出空结果。**同一条命令换成文件路径就能看到 7 行**，所以「无持有者」是假阴性，R364 的归因成立。
- **锁类型实测**：对同一把锁做非阻塞尝试——取 `LOCK_SH`（共享）**成功**，取 `LOCK_EX`（排他）**被拒**。⇒ 6 个常驻进程各自持有**读锁**（消费缓存），`prune` 要写锁 ⇒ 必然阻塞。这就把 R364 的「现象观察」升级为「可解释的机制」：**只要还有任何 `uv tool` 常驻进程，`prune` 就不可能成功，与超时时间长短无关**。
- **prune 复测（本轮，有界）**：给定 25 s 上限，进程零输出、未自行退出，被 `SIGKILL` 回收 ⇒ 阻塞复现。配合上面两条，无需再用「有无持有者」猜测。

### 2.2 因此的处置原则

- 想用原生 `uv cache prune` 回收，**必须下线的服务**（你批准才做）：`hindsight-api` daemon（pid 3046，端口 9077）、`mcp-server-aliyun-observability`（34773/42617/10815）、`redis-mcp-server`（11523/34952）。
- 不想停服务 ⇒ 走本轮的手工子集路线（已在用、近 3 天、路径前缀三重闸；见 §3）。

## 5. 账目差额归因：为什么 `du` 少了 14.7 G 而 `df` 只多了 3 Gi

- 事实：`du -sh ~/.cache/uv` 21 G → 6.3 G（−14.7 G）；同期 `df` 可用 14.45 Gi → 17 Gi（+3 Gi 左右，容器级可用 18.5 GB）。
- 排查与排除项：
  - **本地快照？** `tmutil listlocalsnapshots /` 只有 3 条 `com.apple.os.update` 系统更新快照（非用户数据快照，且是既有的）⇒ 不构成主要占位。
  - **并发写入？** **是。** `iostat -d disk0 1 5` 连续 5 个采样：**25.45 / 29.97 / 35.16 / 157.34 / 38.32 MB/s**（持续 25–38 MB/s，一根瞬时 157 MB/s）。按 30 MB/s 估，5 分钟就写掉 ~9 GB —— 与「14.7 − 3 ≈ 11.7 G」的差额同量级。
  - 同窗口内确实被修改的大文件（>300 MB，30 分钟内）：`Library/Group Containers/HUAQ24HBR6.dev.orbstack/data/data.img.raw`（OrbStack 稀疏镜像）、微信 `db_storage/message/{message_resource,message_fts,biz_message_0,message_2}.db`、`projects/GenericAgent/logs/feishu_agent.log`、`~/.pg0`（hindsight 的向量库）。
  - 且并行会话在跑：`python3 temp/deepdive_v2/scripts/queue_codex.py LX1 CC1`（它正是上面那些 uvx MCP 进程的父会话）⇒ 本机此刻有多写者并存。
- 结论：**回收本身没有失败**（`du`、清单字节、条目数三口径互证），`df` 的净增被同时段写入「吃掉了」。要让 `df` 真实反映回收量，得在**无并发写的窗口**复测。
