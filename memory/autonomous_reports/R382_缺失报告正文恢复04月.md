# R382 缺失报告正文恢复（2026-04 月度 zip 试点）

- 时间：2026-09-24
- 任务来源：TODO L12「缺失报告正文补全」（评审 6/10）
- 边界（本轮自我约束）：**只做 1 个月度 zip**；产出「可恢复 / 不可恢复」双清单；不覆盖任何已有正文（sha256 判重）；零新增定时任务；**不写 memory 报告树**（入仓属人工审批项）。

## 1. 问题与根因

- 现状：`memory/history.txt` 有 **349** 条编号记录，而两树（`memory/autonomous_reports/` + `temp/autonomous_reports/`）在盘正文并集仅 **122** 份，缺 **236** 条正文（工具自报口径，见下方原始输出）。
- 根因：早期（4–5 月）报告由 `code_run` 脚本**内联**写盘——正文以 `report = """..."""` 字面量存在脚本里，再 `Path('temp/autonomous_reports/R<N>_*.md').write_text(report)`。历史归档工具 `harvest()` 只认 `file_write`/显式报告路径，**不抓这种内联写盘**，故命中率≈0。
- 关键安全约束：这些会话日志里的脚本**含 `complete_task`/推送调用**，**绝不可执行**；只能做 `ast` 静态解析，从字面量还原正文。

## 2. 方法与工具

工具：`tools/report_body_recover.py`（本会话新建，纯 stdlib，默认 dry-run）

- `scan`：静态解析月度 zip 内每个会话成员的 `code_run` 代码块与 `file_write` 调用，抽取内联报告字面量作为候选；输出四桶 + JSON。
- `apply`：把可恢复候选写入 staging 目录，sha256 判重，已存在且内容不同标记 `conflict`（不覆盖）。
- **编号规则（本任务最关键的一处修正）**：早期会话的「正文 H1 里的编号 / 文件名前缀编号」**不是规范号**（各会话自编号，实测偏移 0 占 65、+1 占 20、+7 占 6）。因此编号改为**机械对账**：把正文 H1 与 `history.txt` 的标题做词集合打分，取最高分条目定规范号；H1 自编号/文件名号只作"假设号"，同分时优先假设号（该修正把可恢复数从 99 提到 105，并消掉 1 例明显错配 R68→R284）。

复跑命令：

```
python3 tools/report_body_recover.py scan  --zip memory/L4_raw_sessions/2026-04.zip --json temp/recover_04g_scan.json
python3 tools/report_body_recover.py apply --zip memory/L4_raw_sessions/2026-04.zip \
        --out temp/recovered_04 --manifest temp/RECOVERY_MANIFEST_04.json
python3 temp/gen_lists04.py      # 生成双清单 markdown
```

## 4. 校验（自证，不只跑通）

1. **编号唯一性**：105 条规范号去重后仍 105，范围 R8–R304，无重复占号。
2. **不与在盘正文冲突**：工具内部先算「在盘正文编号集合」，与之对账的 16 条被单独分桶、不写盘；staging 目录清空后重跑 `written=105 skipped=0`（首次重跑出现的 97 条 `conflict-existing-differs` 是上一版匹配器留下的旧文件所致，清 staging 后消失——这本身也是"改匹配器必清 staging"的证据）。
3. **正文成色**：字节 min 362 / 中位 1307 / max 5595，**无 <200B 碎片**。
4. **日期窗口**：按来源成员日期前缀（0424/0427/0428）与 history 月份逐条比对，无跨窗口错配报警。
5. **未执行任何被解析脚本**：全程 `ast` 静态解析；无 `complete_task`、无推送调用被触发（本轮无任何外部通知动作，最终落账时由 `helper.complete_task` 自带 1 条推送，属既有行为）。
