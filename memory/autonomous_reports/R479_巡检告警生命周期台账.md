### 1.1 为什么不是「每小时一行」——接线状态是决定性证据

`reflect_scripts/09_task_freshness.py` 自己的文档字符串已把这条钉死（逐字引用）：

> 本文件的存在不等于「已接入」：reflect_scripts/ 下没有目录自动扫描（已实测：每个脚本靠各自的 launchd `agentmain.py --reflect <script>` 驱动）

而 `reflect_scripts/*.py` 由 `agentmain.py --reflect <script>` 逐脚本常驻（`agentmain.py:221/282`），因此**每个反射脚本要有自己的 launchd 条目才会跑**。实测本机注册面（`~/Library/LaunchAgents/`）引用到的脚本只有四个：

```
com.cuip.genericagent-autonomous.plist : reflect/autonomous.py
com.cuip.genericagent-l2-gate.plist    : reflect_scripts/07_l2_gate.py
com.cuip.genericagent-price-alert.plist: reflect_scripts/06_price_alert.py
com.cuip.genericagent-scheduler.plist  : reflect/scheduler.py
```

`09_task_freshness.py`（声明 `INTERVAL = 3600`）**零命中**：没有 plist 引用它、也没有其它被调度脚本拉起它。⇒ 台账只在**人工会话里跑工具时**才落行，这正是「7 行 / 3 天、间隔中位 19.10 h」的成因，与 R411 遗留的待批项（「未接线定时待批 `DECISIONS_R411_task_freshness.md`」）互为印证：**工具+反射脚本都写好了，缺的是那一行调度注册**。

### 1.2 反面教训：日志里的关键词计数**不是**运行痕迹

我在取证早期犯了这条错，记录下来：`zgrep -c '09_task_freshness'` 在反射日志归档里给出 41 / 26 / 53 三个非零值，看着像「一直在跑」。逐行看内容后确认命中全是**会话文本回声**（L1 记忆正文、TODO 原文、`file_patch` 参数回显），而真正的脚本自报行应形如 `^\[09_task_freshness\]`：

- 活日志 `logs/autonomous_reflect.log`：锚定命中 **0**；
- 归档 `logs/archive/autonomous_reflect.log.*.gz`：锚定命中 **0/0/1/0/0**（仅 09-26 那份有 1 次，属人工运行）。

⇒ 判「某脚本/任务是否在跑」必须用**该脚本自己的行首标记**或副作用（台账 mtime / 行数），不能用裸关键词计数——GA 的日志里混着完整 L1/L2/TODO 文本，裸词命中率天然虚高。

### 3.2 三条必须一起读的口径声明（禁单独引用某个比率）

1. **处置率/复发率是「台账差集」口径，不是人工处置确认**：`CLEARED` = 该目标的硬问题 id 在后续行中消失。实测里 birdie 显示 `CLEARED ←复发`、haisou `CLEARED`——这两个目标在 R442/R459 里的独立结论分别是「站点侧不可达、建议退役（待批）」与「站点侧抓取失败」，即**它们从硬问题列表消失≠故障已修**。⇒ 报告若引用「处置率 1.0」必须同句标注此口径。
2. **持续时长 0.0 h 是粒度伪影**：轮次间隔中位 19.10 h 且事件只有 1~2 轮在场，天/小时粒度的「持续时长」无统计意义；台账补上定时后才可复算。
3. **analyze 与 rounds 是两层不同源，不可互相校验**：analyze 消费台账（判定流水），rounds 重建 L1 证据序列（44 目标 / 28 天）。因此「analyze 有 3 事件」与「rounds 有告警轮 0」并存不是矛盾，而是**台账面 vs 重建面的互补**；真正把两者钉在一起的是 reconcile（重建 vs ground truth）与 crosscheck（本器重建 vs 真工具同层判定，DIVERGE 0）。

### 3.3 与相邻工具的边界（复用而非重写）

- `tools/task_freshness.py`（R411/R464/R470/R475）：**生产者**，负责三层判据 + 写台账；本器只**消费**，零判据复制。
- `tools/content_change_detector.py`（R457/R470）：查「写了但内容没变」；本器查「告警出现→持续→处置→复发」。
- `tools/detector_replay.py`（R467）：按已知坏窗口回放各层判据 → 得「各层延迟/盲区」；本器 reconcile 与它**同结论但不同路径**（R467 从坏窗口侧量漏报，本器从重建序列 × gt 侧量），互为独立印证。
- `tools/notify_receipt.py`（R459）：判「推送是否真送达」；本器判「告警生命周期」，不碰推送。

## 4. 本轮顺带修掉的三个真缺陷（均由真跑暴露）

1. **豁免判定双路径不一致**：豁免（`target_exempt`）原先只在「重建路径」生效，导致 `wechat_13h_0704_0927` 这类 disabled 用例在另一条路径被当漏报（84 天 L1 有信号却判 0 episode）。修法=**单一源 `target_exempt` 优先判定**；NC17/NC18 断言同步更新。
2. **NC18 断言方向错**（自证式负控设计缺陷）：初版「整表位移后应出现 N 个 FAIL」与重建语义不符（位移只加宽 gt 窗口，盲区仍是盲区）。改为**「坏窗口冒充正控必须 FAIL」**——即负控必须能被证伪，而不是指望一个不可能发生的结果。
3. **真分支缺 `import subprocess` = selftest 假绿**：`crosscheck` 真跑（真调工具）分支在 selftest 里全走 `--from-file`（喂预制 JSON）支路，所以缺 import 的崩溃**从未被覆盖**，裸跑才炸。这又是一次 RULE16 的实例（「测试全绿」先证测试真执行）。修法=补 import + 新增 **NC26 静态 import 门禁**（扫「模块被当 `X.` 用却没 import」）。★连带发现：NC26 自身用了 `re` 而未 import，把 selftest 直接跑崩——同一类洞的第二层；补 `import re` 后 29/29。
