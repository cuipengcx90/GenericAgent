## 5. 事故：8899 站「只有局域网能开、本机 127.0.0.1 打不开」

症状：浏览器访问 `http://127.0.0.1:8899/` 得到的是 anyrouter 的 WAF 反爬页（而非归档站），但 `http://192.168.1.13:8899/` 正常返回看板。

判定链（每步都用可复现命令，不靠猜）：
1. 读 plist `com.cuip.archive-server.plist` + 启动脚本 ⇒ 真身是标准 `http.server`，不可能是「HTTP/1.1 + 两套 Server 头」的应答。
2. 对照实验：回环响应头同时出现本地 `BaseHTTP` 与阿里 `ESA` 字样 ⇒ 说明**回环流量被另一进程接管**。
3. 本机无 `lsof`/`netstat`，改用 Python 枚举进程与监听地址 ⇒ 命中 `pid 60823`，命令行 `/tmp/anr_proxy.py`。
4. 读其源码：显式 `bind 127.0.0.1:8899`，把回环请求转发到 anyrouter ⇒ 与症状完全对应（LAN 地址不经过该绑定，故正常）。
5. 取真实 LAN IP 时须避开 Clash 假 IP（`198.18.0.1`），从 `ifconfig` 读 `192.168.1.13`。

处置（保守、可逆）：先落审计文件 `temp/anr_proxy_stale/audit.json`（记录 pid/启动命令行/端口/近数小时 dump 归属），确认近期 dump 只剩我自己的测试与误撞流量、无他人活跃使用后，对该精确 PID 发 SIGTERM。**脚本本体保留在 /tmp**，如需恢复抓包：`python3 /tmp/anr_proxy.py`。

恢复判据（双通道）：`127.0.0.1:8899` 与 `192.168.1.13:8899` 均返回标准 `SimpleHTTP` 200、字节 53980（与看板一致）。

★通用教训：**「本机回环端口被别的进程抢占」是网页抓包代理类遗留件的典型副作用**——症状伪装得像站点被封/被劫持，实际是本地端口冲突；排查顺序应为「真身进程命令行长什么样 → 谁绑的端口 → 该绑定是否含 127.0.0.1」。同类残留物（另会话调试用）今后一律先留审计再停，并把恢复命令写进审计文件。

跨源采集扩展（这是用户要的「可扩展」）：
- 加一个采集站 = 在 `tools/course_sources.json` 增一条记录（`add-source` 子命令写，或直接编辑），字段：`id / name / url / parser / detail / channel / kind / disabled / note`。
- `parser` 决定如何从该站页面抽课程列表；`detail` 决定是否进入详情页二次抓取；`channel` 是通道优先级（browser → jina → http）；`disabled: true` 可临时停用而不删配置。
- 抓取入口统一为 `course_pool.py fetch --source <id>`（`--include-disabled` 才跑停用源）⇒ 主流程无需为每个站改代码。

跨源搜索扩展（P2 方向）：现有「海搜 / 盘搜 / 全能（quangneng）」三路各自独立脚本；P1 已把「全能」的课程列表接进池（作为 search 侧的一个源），后续新搜索源同样以注册表条目接入，池内按 course_id/标题归一 + `dup_groups` 暴露重复，避免同一门课被多源重复学习。
