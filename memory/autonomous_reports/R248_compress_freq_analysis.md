## 风险评估

| 风险项 | 评级 | 说明 |
|--------|------|------|
| 逻辑变更 | 🟢 无 | 仅改频率门控，压缩逻辑不变 |
| 性能开销 | 🟡 低 | LLMLingua 在 CPU 上约 50-200ms/次，每轮多触发 1.5 次平均增加 ~150ms |
| 压缩过激 | 🟡 低 | `keep_recent=10` 保护最近10条不压缩，历史消息才被截断 |
| 信息丢失 | 🟡 低 | 已有 `max_len=800` 截断保护，不会完全删除内容 |
| 回滚难度 | 🟢 极低 | 单行改动，git revert 即可 |

## 已有沙箱验证

`compress_sandbox_test.py` 已存在（之前某轮创建），对比了 `%5` vs `%1` 的效果：
- 构造 50 条含长工具返回的模拟消息
- 验证了压缩逻辑正确性
- 结论：`%1`（每轮压缩）在模拟场景下节省 ~60% tokens

`%2` 是 `%1` 和 `%5` 之间的平衡点，兼顾效率与性能。

## 建议的代码改动

```diff
# ../llmcore.py line 68
-    if compress_history_tags._cd % 5 != 0: return messages
+    if compress_history_tags._cd % 2 != 0: return messages
```

**改动范围**：1行，1个字符（`5` → `2`）

## 结论

- **当前状态**：`%5` 门控导致 80% 的轮次跳过压缩，历史消息持续膨胀
- **改动收益**：2.5x 压缩频率，预计额外节省 ~1.09M tokens/历史周期
- **改动风险**：极低（单行，可秒级回滚）
- **建议**：批准执行 `%5→%2`，观察 7 天后产出效果报告
