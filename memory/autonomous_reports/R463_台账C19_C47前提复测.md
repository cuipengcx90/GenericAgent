## 3. 方法

四类判定的语义：

| 判定 | 含义 | 本批判据 |
|------|------|----------|
| CLOSE | 前提消失 ⇒ 建议关闭 | 声明要改的目标已含该内容 / 目标已不存在 / 环境已变 |
| REWRITE | 声明过期 ⇒ 建议重写 | 意图仍在，但声明的目标名/落点/输入已被别的载体取代，或声明的事实已被推翻 |
| ACTIVE | 前提仍成立 | 逐条机械探针给出的前提仍为真 |
| MANUAL | 无机器可判前提 | 价值取舍 / 政策口径 / 需求确认 |

实现要点：

- **数据驱动探针**：每条 = 「目标类型 + 探针类型 + 期望值」的声明（文件存在性 / 内容 token / 大小阈值 / 端口监听 / 进程存在 / 调度条目 / enabled 标志 / 缓存体积），新增条目只加一行数据，不改判定内核。
- **复用内核、零重写**：台账行解析直接 `import` 既有 `temp/pending_decisions/pending_evidence.py` 的 `parse_ledgers`（行 ID 键为 `id`，非 `_id`）。
- **fail-closed**：台账内不存在的 ID 判 `UNKNOWN_LEDGER`，不静默当通过（负控 NC8）。
- **口径自证**：缓存体积一律走 `du -k` 已分配块，稀疏文件不计入（负控 NC10 用一个逻辑 2GiB 的稀疏文件证明不误判）。

探索过程中的一个真坑（写入本文以省后来者一轮）：

- C19 的台账声明里写的是「日志压缩脚本改指 `tools/log_compress.py`」，但初版探针用 `grep 'temp/'` 在 `helper.py` 里找，命中 0 ⇒ 判「已应用」；同时另一探针 `grep 'compress_log'` 命中 ⇒ 两条证据自相矛盾。**真因**：`helper.py` 用 `_TEMP_DIR` 变量拼接路径，故字面 `temp/` 不出现。改为探真写法（`tools/log_compress` 是否存在 / `compress_log.py` 是否仍在引用）后判定才自洽。**教训**：台账声明里的路径字面 ≠ 源码里的路径字面，探针必须打「真实写法」而不是「声明措辞」。
