### 3.3 实验结果：终态大小
实验输出：

- `%5: 155412 -> 65740 chars, save=57.7%`
- `%2: 155412 -> 65740 chars, save=57.7%`
- `%1: 155412 -> 65740 chars, save=57.7%`

结论：
- 在该简化模型下，**最终压缩后的终态大小一致**
- 因为被压缩的旧消息集合最终趋同，差异不体现在最终结果本身

### 3.4 实验结果：逐轮生效时机
逐轮大小如下：

- `%5`: `[155412, 155412, 155412, 155412, 65740, 65740, 65740, 65740, 65740, 65740]`
- `%2`: `[155412, 65740, 65740, 65740, 65740, 65740, 65740, 65740, 65740, 65740]`
- `%1`: `[65740, 65740, 65740, 65740, 65740, 65740, 65740, 65740, 65740, 65740]`

关键发现：
- `%5` 要到第 **5** 轮才开始压缩
- `%2` 第 **2** 轮就开始压缩
- `%1` 第 **1** 轮即生效

因此频率优化的真实收益是：

> **更早抑制上下文膨胀，减少压缩前几轮的高 token 暴露窗口**  
而不是让最终压缩后的大小继续下降。

## 4. 结论与建议

## 4.1 主结论
如果要实施 R220 的 P0 方案，建议仍以：

- `../llmcore.py` 中 `compress_history_tags._cd % 5`
- 调整为 `% 2`

作为首选待审方案。

原因：
1. 能明显提前压缩生效时机
2. 相比 `%1` 更温和，风险更低
3. 与 R229 的既有建议一致，便于延续历史结论
4. 回滚成本极低（单行恢复）

## 4.2 不建议直接上 `%1`
虽然 `%1` 更早触发，但存在潜在问题：
- 压缩过于频繁
- 调试与阅读历史信息可读性可能更差
- 若后续引入更重的压缩器，额外调用开销更高

因此 `%1` 更适合作为：
- 二阶段观察后的备选方案
- 或在 `%2` 效果不明显时再考虑
