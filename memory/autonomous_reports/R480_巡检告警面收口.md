## 1. 结论（先说结果）

1. **跨轮比较改用「稳定事件 ID」**：`task_freshness` 每轮产出的告警项现在带 `event_ids`/`event_details`，事件 ID = `ev-<12 hex>`，取值为**规范化 JSON `{scope,target,face}`（sort_keys + 紧凑分隔符）的 sha256 前 12 位**（`alert_event_id.py:105-110`），与「哪一轮」「第几次」无关 ⇒ 同一问题跨轮是同一条事件，重复推送与幻影「已恢复」都被结构性消除。
2. **幻影「已恢复」根治（本题真 bug）**：台账顶层 `event_ids` 曾把**非硬目标（OK/INFO 行）**的事件也并进去，而消费端（09 反射器）只统计**硬目标**事件 ⇒ 两侧键空间不对称，会把「上一轮 OK 行贡献的事件」报成「本轮已恢复」。已在**生产端与读取端两侧同时收紧**，并新增**独立不变量审计**（第三方复算器）把它变成可机械检测的契约。
3. **坏/正窗口回归集落地**：新增 `tools/freshness_regression.py` + 用例表，把 R467 回测出的 4 个已知坏窗口 + 2 个正控固化成可一键复跑的基线闸门（`fn_cases=0 fn_cells=0 fp_cases=0 delay_regs=0 覆盖 8/8`），并带 4 类负控证明「关掉某层必然漏报/基线被篡改必然报退化」。
4. **只读边界守住**：全部子命令零写入；真实台账（`temp/task_freshness/ledger.jsonl`，7 行，sha256 前16 `dc60b6e3c3b436e6`）在全部实验前后逐字节不变（前后 sha256 相同）。

## 3. 根因与修法（本题核心）

**现象**：09 反射器会把某些问题报成「已恢复」，但真实环境里该问题并没有被修过（幻影恢复），且该幻影可复现于两轮自测之间。

**根因**（两侧口径不对称）：

| 侧 | 旧口径 | 问题 |
|---|---|---|
| 生产端 `task_freshness` 顶层 `event_ids` | 并**所有**目标的事件（含 OK/INFO） | 顶层集合 ⊋ issues 集合 |
| 消费端 09 `_keys_of_record` | 只统计**硬目标**事件 | prev 键集含幻影、now 键集不含 ⇒ 差集报「已恢复」 |

**修法**（三处，缺一不可）：

1. 生产端：顶层 `event_ids` 只并硬目标事件（`all_ev` 口径收紧）。
2. 读取端：`_keys_of_record` 一律从 `issues` 派生（兼容历史行，历史行没有 `issues` 时回落旧 id 空间）。
3. 新内核：`audit_ledger()` 把「顶层 == issues 派生」写成**不变量**，供第三方独立复算（不依赖 09 的实现细节）。

**为什么这不是「让报警消失」**：负控已证 —— 用**修复前口径**对同一幻影行重算，幻影必然出现（见 §4.4 的反事实断言），且 `audit` 对幻影行报 `violations=1 / top_only=[ev-top-ghost]`；修复后同一行键集为空、e2e 的「已恢复」为 0 条。
