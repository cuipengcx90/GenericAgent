## 2. 证据（逐条可复跑）

### D1（P0）守护重启风暴把「段满休息」归零

- watchd 日志 281 行分类计数 `{'RESTART': 35, 'OK': 179, 'RESTART_SKIP': 67}`，首行 `[2026-10-06 01:31:08] RESTART DAEMON_DEAD`（文件 `temp/bg_task/logs/linuxdo_browse_watchd.log`）。
- 停滞判据取自 browse_log 新鲜度而非 stdout：`10:49:43 − 00:15:14 = 38069s`，与日志中 `RESTART STALLED_38069s` **逐秒相符** ⇒ 判据本身正确，它确实看见了「零产出」。
- 但处置是「杀掉并重启」：daemon 的段计时是进程内变量（`tools/linuxdo_browse_daemon.py:1165 start = time.time()`、`:1264` 判 `max_session_min`、`:1268` 重置）⇒ 每次重启即归零。9h20m 内 35 次重启，110min 段满几乎不可能达成；今日仅在 10:51:56 首次达成一次（stdout 原文 `[2026-10-06 10:51:56] 单段运行满 110min，休息 46min`）。
- 与 10-05 实盘互印：当日 102 帖、跨度 21.05h、相邻间隔中位 404s、>600s 仅 10 处、≥25min 仅 2 处（静默窗 414.7min、风控暂停 148.3min）⇒ 当日**没有一次真正的段间休息**（内核档位 rest 应为 1500–3200s 量级）。

### D2（P0）连续 10.5 小时零产出，且监控面显示「健康」

- browse_log 末两条：`{"ts": "2026-10-06 00:13:28", "st": "FAIL", ...}`、`{"ts": "2026-10-06 00:15:14", "st": "FAIL", ...}`；全档 118 行 / 22984B ⇒ 00:15 之后（含 09:01 重启后的整个上午）零条浏览记录。
- stdout 逐字：09:01:36 / 09:17:48 / 09:29:37 / 09:47:15 四条 `RC_NO_SESSION_RETRY: 浏览器桥无任何会话（Chrome 未运行 / 扩展未连接 / 驱动未启动？）（n/6，睡 Xmin 后重试）`；随后 10:06:48–10:46:55 每 301s 一行 `用户在前台看 linux.do，跳过本轮浏览，睡 5min`。
- 告警面缺位：watchd 有 `FAIL_STREAK_NOTIFY` 与飞书通道，但「重启成功」被记为 OK（179 条 OK）⇒ 重启风暴在监控面上呈现为健康，用户无感知（本报告是首次把这个组合定性）。

### D3（P1）「五动作共用同一随机内核」未落地

- 内核 `tools/linuxdo_antidetect.py:45-48`（browse 档）：`seg_n=(3, 5)`、`seg_len=(45, 110)`、`gap=(110, 260)`、`gap_long=(300, 600)`、`gap_long_p=0.30`、`rest_p=1.0/7.0`。
- daemon `tools/linuxdo_browse_daemon.py:92-94` 另起一套同值常量：`GAP_RANGE = (110, 260)` / `GAP_LONG_RANGE = (300, 600)` / `GAP_LONG_P = 0.30`；生产调用只有 `:1154 time.sleep(hu.action_gap("browse", base=random.uniform(*GAP_RANGE)))`。
- 全仓对 `GAP_LONG_*` 的引用只剩 `:1389` 的 selftest 断言 ⇒ **30% 长休没有任何生产调用点**（死常量），实际长休只来自 humanize 的 6% 分支（×3.5 倍率），约为声明值的 1/5。
- `day_segments`（`:92`，含 seg_n/seg_len）在 daemon **零调用** ⇒ 内核的「一天切 3–5 段、每段 45–110min」在浏览路径上完全没有实现。

### D4（P1）level_log.jsonl 语义污染，「每天查几次」不可证

- `tools/linuxdo_browse_daemon.py:1204 if level_check_due(st):` 之后 `:1208 src = "throttled"` 走的是**同一条写入路径**：节流分支也向 level_log 追加一行，并把 `state.level.ts` 刷成节流时刻。
- 实测：level_log 在 10-06 当天呈 301s 等间隔成串（与 stdout「节流中」逐条对应），最后一次 `ts` 停在 10:46:55。
- 后果：该台账既不能回答「今天检查了几次等级」，也不能回答「几点检查的」（真实检查被节流噪声淹没）；任何基于它的错峰审计都会失真。内核自身（120 天模拟 1 次/天、最小间隔 12.84h、小时分布 8–23）是干净的，问题只在落账层。

### D5（P2）文档/口径漂移

- 内核把「一天切几段、每段多少分钟」作为卖点（`tools/linuxdo_antidetect.py:40` 注释、`:92 day_segments`），但浏览实盘是「单进程 110min 段 + 被重启」，`day_segments` 在 daemon 零调用 ⇒ 文档承诺 > 实现。
- SOP 的「五动作共用同一随机内核」表述，在浏览路径上不成立（daemon 只把**等级检测**委托内核；浏览节奏自带第二份实现，见 D3）。
- daemon docstring 声称的 30% 长休未接线（见 D3），属「文档内嵌数值未随实现回填」的同类问题。

## 3. 建议（补丁级，均不改变站点行为语义）

1. **段计时持久化（解 D1）**：把 `start` 落进 state（`st["seg_started_at"]`），并在每次 `_save_state` 时刷新；重启后按「剩余段时长」继续而非归零 ⇒ 重启不再摧毁段级节律。判据：重启后 stdout 仍能出现「单段运行满 110min，休息 Nmin」。
2. **watchd 停滞判据与处置解耦（解 D1/D2）**：当前「browse_log 不新鲜 ⇒ 重启」。建议引入第三种处置：若 stdout 最近 10min 内有 `RC_NO_SESSION_RETRY` 或「用户在前台」行，则**判因不判量**——标记 `BLOCKED_ENV`（不重启、只升级为一次飞书告警，冷却 6h），避免把「环境不可用」当「进程卡死」反复重启。
3. **长休接线（解 D3）**：把 `:1154` 的 `random.uniform(*GAP_RANGE)` 换成 `hu.action_gap("browse", base=...)` 带内核长休分支（或直接委托 `antidetect.next_wait`），并删除 `GAP_LONG_*` 死常量与二次实现；单源化后 daemon 私有常量应清零。
4. **台账分列（解 D4）**：节流行改写入 `state.throttle_log` 或 level_log 的独立文件（`src=throttled` 单列），**只有真检查才写 `OK/` 与 `state.level.ts`**；否则任何「检查频次」审计都不可用。
5. **文档回填（解 D5）**：SOP/注释里「共用同一随机内核」「30% 长休」「一天 3–5 段」三处按实现回填或标 ⬜ 未实现（同 R530 通则：规格内嵌真值随实现同步）。
