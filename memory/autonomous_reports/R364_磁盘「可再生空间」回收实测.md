## 3. 本轮关键发现：`uv cache prune` 为什么一分钱没回收（已定位，非脚本 bug）

现象：`uv cache prune` 在 240 s 内 **CPU 时间 0.01 s、0% CPU、无任何输出**，被超时强杀。

取证（`/usr/sbin/lsof -p 62594`）：

```
uv 62594 cuip 9u REG 1,18 0 252820895 /Users/cuip/.cache/uv/.lock     ← 一直挂在缓存锁上
```

同时存在 3 个**常驻** uv 进程，它们把解释器直接跑在缓存目录里：

```
3046  uv tool uvx hindsight-api@0.10.1 --daemon --idle-timeout 0 --port 9077
5013  ~/.cache/uv/archive-v0/d3N475aL1AuivR67/bin/python …/bin/hindsight-api --daemon --port 9077
34773 uv tool run mcp-server-aliyun-observability …   34952 redis-mcp-server …
```

⇒ 结论：**uv 的 21 GB 不是"可再生但没人用"，而是"正被长驻服务当作安装目录使用"**。所以：

- 本轮**不做** `uv cache prune --force`（会删掉正在运行的 daemon 的解释器，属破坏性）；
- 要回收必须**先停服务**（hindsight-api daemon + 两个 MCP），再 `uv cache prune`；
- 评审处方里"uv 优先 prune 安全子集"的前提在本机**不成立**，已按"停服务 = 需批准"上报。
