## §3 探针设计（`temp/freshness_probe/probe.py`，约 250 行，纯 stdlib）

判据只有一条，但把三类"索引自我声明时刻"都覆盖了：

```
语料侧 = 索引所覆盖的语料集合（globs 展开，或清单文件 list_json 里列出的真实路径）
索引侧 = 索引自称的生成时刻：
         mode=regex  → 从索引文本里正则抓时间（如 INDEX.md 的「- 生成: 2026-09-23」）
         mode=mtime  → 用索引文件自身的 mtime（如 recall_probe/index.db）
         mode=json   → 从索引 JSON 里取字段（如 entries.json 的 corpus.max_mtime）
判定   = 语料最新 mtime > 索引时刻（+容忍差）→ STALE(过期)；否则 FRESH
附加输出 = max(sha16) 语料内容指纹（供二次判据/审计）＋ 清单模式下缺失文件数 ＋ 最新 3 个语料文件
```

- **零副作用**：只 `stat/read`；不 `touch` 索引、不重建索引、不写被检测目录。实测用"被检测文件 mtime/size 前后快照"证明（§4 表）。
- **容忍差**：`--tol-sec N`。用于消除"索引刚构建后 1 分钟内被另一进程追加一行"这类秒级落后（真实场景见 §4 的 history_value 目标：落后 75 秒）。
- **负控 3 例**（脚本自带 `--negctl`，全部为合成夹具，写在 `temp/freshness_probe/negctl/`）：
  1. `fresh`：语料 12:00 / 索引 13:00 → 期望 FRESH ✅
  2. `stale`：**篡改索引时间戳**使其早于语料 → 期望 STALE ✅（这就是 TODO 要求的第 ④ 条负控）
  3. `missing`：索引文件不存在 → 期望「索引缺失」并 rc=2 ✅

## §6 边界、判读陷阱与残余风险

1. **假阳性（本轮实测）**：`recall_index` 恒判 STALE，因为它的语料含 `reflect_scripts/.price_history.json`（price-alert 反射器每 2 分钟改写）。**结论：STALE ≠ 索引坏了**。判读必须看探针打印的「最新 #1 语料」——若它是心跳/日志类文件，应改用排除 glob 或只对"业务分区"计时（→ C64②）。
2. **假阴性**：判据只看 mtime。若索引重建后语料**内容又被改写但 mtime 被保留**（`touch -r` 等），探针会误判 FRESH。故探针同时输出 `max(sha16)` 语料指纹，供二次比对（本轮未接线到自动化，仅打印）。
3. **清单模式的"缺失"**：`recall_index` 清单 1248 个路径中 **5 个已不存在**（多为 temp/ 内被清理的产物）。这不是探针缺陷，而是索引自身已含悬空指针 ⇒ 可作为该索引的**健康度指标**（5/1248 = 0.4%）。
4. **精度差异**：`INDEX.md` 只声明到「天」，故对同日更新**无分辨力**（当天必判 FRESH）；这是索引格式决定的，不是探针问题。
5. **状态型事实的时效**：C57（微信定时任务停机）属"用户随时可能改回"的状态，**一律须写「截至 2026-09-23 实测」**，否则下轮又成过时记忆。
6. **未做（显式边界）**：
   - 未给探针接线（无 launchd / 无反射器注入）——接线属待批（C64③），本轮**零新增定时**；
   - 未写 memory/ 任何文件（C53–C64 全为待批提案，符合 TODO 第 58 行「禁直接改 memory/L1」）；
   - `.ga/l2/index.*` 的探针目标**未纳入**：其生成者/语料边界在本轮未能低成本定位（`grep generated_at` 于 herdr-agents 未命中、仓库路径与本机布局不一致），故只做三个能确定边界的目标（recall/INDEX/history_value），**不猜**。
