## 1. 方法与证据（可复现、零副作用）

1. **只读打开**：`sqlite3.connect("file:<path>?mode=ro", uri=True)`——源库与两份快照都只读，无写、无 VACUUM、无 mtime 变更。
2. **不读密钥**、不写 `memory/`、不改 `sche_tasks/`；报告与原型均落在 `temp/`（cwd）。
3. **Core Data 纪元**：所有时间列需 `+978307200` 才是 Unix 秒（**踩坑实测**：第一版对比式漏加偏移 ⇒ 「近 7 天」窗口失效、返回 09-03 的老数据；改正后覆盖日严格为 09-16…09-22，见 `out6`）。
4. **独立核验 manifest 自称**（不轻信工具自己的结论）：`kc_snapshot.py` 写在 `manifest.json` 的 `objects/distinct_start_days/sha256/integrity` 与独立复算完全一致——

## 4. 与源库的差异（验收③）

### 4.1 三方对照：快照是「当时的滑动窗口切片」，不是「源库备份」

| 状态 | ZOBJECT | 被删(vs 实盘) | 新增(vs 实盘) |
|---|---|---|---|
| 09-22@10:49 快照 | 17463 | **893** | 1623 |
| 09-23@01:20 快照 | 18277 | **893** | 809 |
| 实盘@21:36 | 18193 | — | — |

- 两份快照**对实盘都是少了同一批 893 行**：这 893 行（09-22 快照里的老数据）在 09-23 01:20 时**还在**，到 21:36 已消失。
- 因此：**09-22 快照比实盘多留 893 行 = 4.9% 库容的不可再生数据**；而两份快照之间（跨 14.5 h）**删除 0 行**（`kc_snapshot_diff --a 09-22 --b 09-23` ⇒ rc=0、新增 809 / 消失 0）⇒ **删除是不定期批量发生**，不是每天匀速掉。

### 4.2 逐流保留窗（两次采样一致 ⇒ 判定为「按流的时间窗」）

| 流 | 09-22@10:49 下限(=当天−?) | 实盘@21:36 下限 | 推定窗口 |
|---|---|---|---|
| `/app/usage` | 08-30 18:32（−22.7 d） | 08-31 15:51（−23.2 d） | **≈23 天** |
| `/notification/usage` | 08-25 04:14（−28.3 d） | 08-26 12:06（−28.4 d） | **≈28.4 天** |
| `/display/isBacklit` | 08-25 03:50（−28.3 d） | 08-26 12:04（−28.4 d） | ≈28.4 天 |
| `/bluetooth/isConnected` | 08-25 09:47（−28.0 d） | 08-26 12:09（−28.4 d） | ≈28.4 天 |
| `/app/mediaUsage` | 09-10 17:53 | 09-10 17:53 | 未触发（量小） |
| `/discoverability/signals` | 2024-12-27 | 2024-12-27 | **不裁剪**（1 年半前仍在） |

**口径说明**：表中「−N d」＝**派生值**——`out4` 只输出各流的行数/时间下限/跨度，天数由「采样时刻 − 该流下限」算出（复核：22.68 / 23.24 / 28.27 / 28.29 / 28.04 / 28.40 天，分别对应表内 22.7 / 23.2 / 28.3 / 28.3 / 28.0 / 28.4）。

### 4.3 删除粒度：按「时间边界」切，半日也删

UUID 级被删 893 行分布：

| 维度 | 明细 |
|---|---|
| 按流 | `/app/usage` 475、`/notification/usage` 380、`/display/isBacklit` 24、`/bluetooth/isConnected` 14 |
| 按 start 日 | 08-25 **279**（该流该日全灭）、08-26 139、08-30 11、08-31 **464** |
| 最早/最晚 start | 08-25 03:50:36 / 08-31 15:50:40 |

- `/notification/usage` 08-26 是 **369 → 244（只删 12:06 之前的 125 行）**⇒ 边界是**时间戳**，不是整天；
- `/app/usage` 08-31 是 **842 → 378**⇒ 同一批量里删掉半天（15:51 之前）；
- 08-30 的 11 行（`/app/usage`）与 08-31 的 464 行同批 ⇒ 一次事务跨多个自然日。
⇒ 结论：**按流各自的 `now − 窗口` 作时间边界，逐次批量删除**（不是「删最旧的一天」）。

### 4.4 差分工具原型（本轮新增能力）

`temp/kc_snapshot_diff.py`：

```
python3 temp/kc_snapshot_diff.py --a 2026-09-22 --b 2026-09-23   # 两快照相减
python3 temp/kc_snapshot_diff.py --live                          # 最近快照 vs 实盘
```

- 逐流输出「行数 / 下限 / 新增 / 消失」；把消失行按 **预期删除**（低于该流新下限）与 **意外删除** 分开；
- **意外删除 > 0 ⇒ 退出码 2**（可直接接告警），实测：
  - 09-23 快照 vs 实盘：新增 809 / 消失 893 / **预期 893、意外 0**、rc=0
  - 09-22 vs 09-23 快照：消失 0、rc=0
- **负控**（`temp/kc_diff_negctl.py`，合成夹具，零副作用）：
  - 用例1「只删低于下限的老行」→ rc=**0**（不误报）✔
  - 用例2「删掉近期行（老行仍在）」→ 报**意外删除**、rc=**2** ✔

### 4.5 跨快照合并（为后续「时间线重建」留口）

- 键 = `ZUUID`；两快照并集 = 18277（=较新快照全集）、交集 17463 ⇒ **较新快照完全包含较旧快照的存活行**，合并无需特殊处理；
- 逐行去重 35740 行仅 8 ms ⇒ 若将来要拼「超 28 天时间线」，按 UUID 归并的代价可忽略。
