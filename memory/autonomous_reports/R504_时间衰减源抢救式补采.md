# R504 时间衰减源抢救式补采（第24批 C2 / TODO L205）

- 日期：2026-09-29
- 主题：时间衰减源（wifilog/chrome/kc/pmset）漏采后能否补 —— 把 R495「只判不救」补成「可抢救采数」
- 前置：R483（留存断档探测 `verify`）、R495（数据级覆盖判定 + `salvage` 只判）、R415/R420（四源采集器）
- 落点：`tools/rolling_source_coverage.py`（+181/−6）、`tools/rolling_source_snapshot.py`（+101/−4）、`memory/source_retention/RETENTION_POLICY.md`

## 1. 问题（R495 留下的缺口）

R495 建立了「数据级覆盖判定」：对缺口日在**更晚的快照**里反查该日 time token，能查到就记 `COVERED`（=数据没丢，只是当天没单独落快照），查不到记 `UNSUPPORTED`。

但它只判不救，且有**两处系统性偏差**：

1. `salvage` 是纯判定，不产生任何数据 —— 判完只能是"报告一句"。
2. **wifilog 的探针写死 `today-1`**（`/var/log/wifi.log` 单日轮转 ⇒ 只看得见昨天）⇒ 只要漏采超过一天就一律判 `UNSUPPORTED`，而实际上 `/var/log/wifi.log.N.bz2` 轮转归档里还留着十几天。R495 对 wifilog 09-27/09-28 的 `UNSUPPORTED` 判定就是由此产生的**误判**（本批已作废并改判）。

## 2. 本批改动

### 2.1 采集侧（`rolling_source_snapshot.py`）

- 支持 `.bz2` / `.gz` 归档读取（`bz2`、`gzip` 导入 + `open_maybe_compressed`）。
- 新增 `wifi_source_files()` / `wifi_read_lines()` / `wifi_year_for()`：现行 `wifi.log` **以及**全部轮转归档都算数据源。
- 新增 `_live_oldest_wifi()`：**替代旧的「恒 today-1」**——逐个归档读首行时间戳取最小值，得"最老仍可抽的一天"。探针标记改为 `rotation-archive-first-ts`。

### 2.2 抢救侧（`rolling_source_coverage.py`）

- `salvage_wifilog()`：扫根目录 `/var/log` 下 `wifi.log*`（含 `.bz2`），逐行判日期把属于目标日的行抽出来，写 `<root>/<day>/wifi.log` + `events.json`；`events.json` 复用采集侧的 `parse_wifi_text()`（**产物与当天正常快照同格式**，消费端零改动），并额外写 `salvaged=True` 与 provenance（归档名 + 字节 + `sha256_16` + 行数）。
- `salvage_one()`：把"哪些源、哪些日需要救"的判定收在一处。
- `salvage_ledger_append()`：追加台账 `temp/source_retention/salvage.jsonl`，幂等（同日重跑不重复追加）。
- CLI：`salvage --source/--today/--root/--src-dir/--apply`。**不加 `--apply` 是 dry-run，零写盘。**

### 2.3 三条硬边界（写进代码、写进自测、写进政策）

| 场景 | 行为 |
| --- | --- |
| 归档里也抽不到该日 | 记 `UNSUPPORTED`，落 `missing_lost` —— 这才算真丢失 |
| 抽到 0 行（`EMPTY`） | **不落盘**（连空文件都不写） |
| 任何情况 | **绝不生成占位/插值** —— 伪造一天数据比缺一天更坏 |

## 4. 政策订正（`memory/source_retention/RETENTION_POLICY.md`）

R495 版政策里写着「wifilog 缺 09-27/09-28 = 真丢失、不可恢复」——**与本批实测相反，已订正**：

- §1 新增「抢救层」；§2 表 wifilog 行补「归档可抢救窗 ≈12 天（实测最老 2026-09-17）」。
- §3.1 由「唯一漏一天就永久丢」改为「独立快照 1 天，但**轮转归档可回溯约 12 天**」。
- §4 `salvage` 语义改为「真采 + 台账 + 幂等 + 不写占位」；§5 清单新增第 5 条「抢救成功即留痕」；§6 末条改判为「正确处置是次日立刻 `salvage --apply`」。
- 新增 §7「抢救式补采（R504 已实现）」：给命令、实测数字、复跑判据。

## 5. 边界与残余

1. **归档窗会滚动**：实测最老 2026-09-17 ≈ 12 天，但这是当下快照值，不是固定 12 天 ⇒ 政策里已标注"随轮转滚动，非固定值"。
2. **chrome/kc/pmset 的抢救仍是"补采当天快照"**（源本身还在窗口内），本批没有为它们写归档抽取——因为它们没有轮转归档，只有源窗口。
3. **未接定时**：仍然靠人工/自主轮触发，与 R495 同（D1 待批）。
4. 抢救产物是**派生抽取**（只留带时间戳且日期==day 的行，非源文件全量拷贝）——`salvage.jsonl` 的 `kind=derived-extract` 与 `note` 已逐字声明，避免日后把它当原始拷贝做字节级比对。
