## 1. 要解决的问题（为什么既有四层不够）

R411/R457/R464 已把「任务是否还在产出」拆成四层判据：产物层（mtime/结构）、运行层（缺跑）、日志层（降级签名）、内容层（跑了但内容没变）。四层共同的盲区是**只看产物侧**：任务每天都在落产物（甚至 rc=0），但**它开跑就不可能成功**，因为某个外部前置已经不成立。

真实样本（R467 回测已证 artifact 层对这些窗口 0 天命中）：

| 坏窗口 | 前置失效形态 | 产物侧表现 |
|---|---|---|
| birdie 08-08 起 | 站点 IP 层不可达（R442 裁决） | 每天照常落 done 报告 ⇒ mtime 恒新 |
| x_ai 08-18 起 | 无已登录 x.com 标签 | 每天落报告，内容为空转 |
| haisou 09-25 | 首页 TLS 截断（SSLEOFError） | rc=0 + 「抓取到 0 个课程」静默降级 |
| linuxdo 09-27 | 登录令牌 `_t` 全域缺失 | 停手写阻塞报告，产物形态正常 |

本层做的事：给巡检补一层**开跑前置条件**判据（L0），任一前置 FAIL ⇒ 直接 ALERT，把「产物侧全绿但必不产出」的场景提前抓住。

## 2. 机制

### 2.1 五类探针（全部只读）

| kind | 断言 | 不覆盖（写进登记面 `limits`） |
|---|---|---|
| `chrome_tabs` | Chrome 标签中 URL 含匹配串的数量 ≥ min_count | CDP 标签 id 失效（标签仍在时发生） |
| `cookie_present` | 多 profile 只读扫 Chrome Cookies，**只判某 cookie 名是否存在，绝不读 value** | 会话有效性、CF 挑战、429 限流 |
| `http_endpoint` | 端点 HTTP 状态 ∈ expect_status；传输层异常一律 FAIL | 业务面（额度、返回体语义） |
| `path_exists` | 依赖脚本/清单在盘 | 脚本内部逻辑 |
| `credential_entry` | 委托 `tools/credential_surface.py` 的在册判定（零重写） | 凭证值是否仍有效 |

### 2.2 单一源登记面

登记面**只有一处**：`tools/freshness_criteria.json` 的 `preflight` 段（`schema=ga.preflight_targets/v1`）。早期草稿里的独立 `tools/preflight_targets.json` 已删除（源码注释处明确标注「避免同一登记存在两处」），防止两处漂移。

```text
$ python3 tools/preflight_check.py check
registry OK：目标 6，探针 10 条
cases OK：用例 6
未纳入回测的在册目标（非错误，仅透明度）：['linuxdo_trust_level_check', 'weekly_inspection']
```

`check` 会把「在册但未纳入回测」的目标列出来（透明度而非错误），NC33 另有一条断言防止「回测覆盖的 target 与在册登记脱钩」。

### 2.3 接入 task_freshness（L0 层语义）

- 前置 FAIL ⇒ 该目标 verdict 升 `ALERT`，并进 `hard_issue_ids`（与既有硬问题同一出口）。
- 前置全 PASS ⇒ **不得判健康**：verdict 不改（沿用既有各层结论），只带出 `preflight` 段与 `health=False`，note 逐字为「前置可用≠产出正常（不得据此判健康）」。
- 未登记前置的目标 ⇒ 完全不出现 `preflight` 段（默认行为逐字不变）。
- `--no-preflight` 开关 ⇒ 关闭本层，回到接线前的判定。
- 消费者不变：`reflect_scripts/09_task_freshness.py` 调的就是 `tools/task_freshness.py`（不新增调度、不改消费者）。

## 4. 边界与未做（显式声明）

1. 探针只判**存在/可达**，不判**有效**：`cookie_present` 命中 ≠ 会话有效（SOP 已记 connect.linux.do 的 `auth.session-token` 是独立会话，不可与本探针互推）；`http_endpoint` PASS ≠ 业务可用（haisou 的额度耗尽、首命中即 403 属任务内部面）。
2. 每个目标的探针边界逐条写进了登记面 `limits` 字段（随 JSON 输出带出，读报告的人能看到「本层不覆盖什么」）。
3. birdie 的 FAIL 与 R442 退役裁决一致，但**本层不代行退役**（退役动作仍在待批台账）。
4. 覆盖 6 个目标（≥3 真实任务已满足），未做扩面；扩面=往登记面加条目即可，但「加哪些」属估值判断，留给后续批次（可复用 R438/R467 的坏窗口清单）。
5. 未新增调度、未改既有四层判据、未改消费者（reflect/09 自动继承）。

## 5. 过程中踩到的坑（供复用）

1. **参数名不对齐**：探针的路径必须写在 `probe.params.paths`（复数、在 params 内），夹具里先写成顶层 `path`，自测报「params.paths 缺失」——按 kind 分派的地方参数名要一次对齐。
2. **回测与登记脱钩**：早期用例集与登记面是两份文件，NC33 专门断言「回测覆盖的 target 必须在册」，否则会出现「回测绿但登记里没这个目标」的假绿。
3. **废弃登记面必须真删**：改成单一源后，旧文件仍留在盘上（未跟踪），一旦有人读它就等于两处登记，已删除。
4. **`replay.json` 里 `cases` 是整数（用例计数=6）而非条目数组**，逐条明细在 `rows` 键（我第一版脚本按 `cases` 迭代，直接 `TypeError: 'int' object is not iterable`）——读 JSON 前先打印 keys，别按名字猜结构。同类：`probe.json` 每个目标的整体结论键是 `agg`（不是 `verdict`），每条探针自身的字段是 `verdict/detail/ms`（不是 `status/elapsed_ms`）。
5. 全量 A/B 时 with 档 12.1s / without 档 0.3s：真探针（尤其 http_endpoint）是耗时主体，`--no-preflight` 可用于快速回归。
