### ② 消费者场景可量化收益 ✅（两条，含一条**否定结论**）
**消费者 A：trendradar 热搜 → 云端报告的前置预筛**
```

```
**消费者 B：haisou 关键词命中 → 相关性闸门**（语料 `haisou_seen_items.json` 1422 对）
纯启发式基线：放行 375（26.4%），其中「仅靠通用词放行」的假阳 70 条，另有假阴 123 条。

| 方案 | 拦假阳 | 正常样本保留 |
|---|---|---|
| 1.5B + 现状 prompt | 9/30 = 30% | 17/20 = 85% |
| 1.5B + 多规则 prompt | 25/30 = 83% | **8/20 = 40%（误杀）** |
| 1.5B + 长规则 prompt | 0/6（**恒定输出故障**） | 20/20 |
| 1.5B + 短句「这是娱乐内容吗」 | 3/6 = 50% | 19/20 未误判 |
| **3B** + 现状 prompt | **12/30 = 40%** | 15/20 = 75% |

**结论（建议采纳）**：**不要**把本地小模型装成 haisou 的语义硬闸门。增大到 3B 只把假阳拦截从 30% 提到 40%，却把正常样本保留从 17/20 压到 15/20；更激进的 prompt 更糟（误杀 60%）。修 `is_relevant` 应走**规则层**（对「AI剧/短剧/小说/漫画/游戏/影视」这类**形态**做正则 + 白名单/黑名单），投入产出远高于本地模型。
消费者 A 可用，但必须先做**影子模式**（只记录"将被丢弃的条目"不动线上），跑 3–5 天核对误丢率再启用。3B 的影子结果已暴露风险：它把 `【早报】…SpaceX拟收购光模块公司`、`下周重磅日程…半导体涨价潮` 也丢了 ⇒ 大模型≠判得准。

## 二、过程与关键教训（可复用）

1. **下载源**：HF 与 hf-mirror 本机同为 ~350 KB/s 且两次断流；**ModelScope 直连 6–7 MB/s（15–17 倍）**。大文件一律优先 ModelScope。
2. **断点续传坑**：`curl` 报 `partial file` 退出码 18 属常态，须 `-C - --retry 5 --retry-all-errors` 循环重试；续传需按"目标名 + `.part`"分离，完成后校验 size 再改名。
3. **★最重要教训（会误导后续所有本地模型判定类任务）**：**1.5B 面对多行"规则式" prompt 会退化为恒定输出**——对 4 条差异极大的标题输出同一个字，且与 max_tokens 无关（32 token 同样）。排查法：**必须同批逐条打印 raw**；只看聚合命中率会把它误判成"能干活的闸门"（本轮就先误判了一次：C 变体报 0/6，其实是全量恒定）。
4. **服务健康检查要两层**：`/health`（服务活着）+ 一条**已知答案探针**（`1+1`→`2`，模型活着）。否则会把"模型答错"误诊为"服务挂了"。
5. **后台长任务**：`setsid` 式脱离会话启动 + 自序列脚本（等文件→起服务→bench→评测→`ALLDONE`），单条 `ls/tail` 轮询即可，不阻塞通道（本轮 3B 全流程无人值守跑完）。
