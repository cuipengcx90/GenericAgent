## 4. 自查发现的坑（本轮实测，写进工具注释）

1. **积压天数必须单一源**：初版自算「来源列 MM-DD → 文件 mtime」，与权威 `view_pending.parse_file` 的三级链（来源列 → 台账头部**生成时间** → mtime）**不一致**——`DECISIONS.md` 的 C1/C11/C14/C19 权威口径 5 天，我报 2 天（根因=该台账头部有「生成时间 2026-09-22」）。改法：直接调 `view_pending.parse_file()` 取 `_src_date` 建 (台账文件名, ID) 索引；取不到才本地近似并**显式标注「本地近似」**。修后逐条复核：C1/C11/C14/C19=5 天、D1=0 天，**与权威逐条一致**。
2. **静默 except 吃掉 NameError**：索引搭建处漏 `import pathlib`，`parse_file` 抛 `NameError` 被 `except Exception: continue` 吞掉 ⇒ 索引恒空、积压全部悄悄回落本地近似（**输出看着正常**）。已改为**硬告警**：复用件在却一条都没建成时打 `[WARN]` 并列前 5 条异常。★同类教训：任何「查不到就回退」的分支都必须留可见证据。
3. **CLI flag 扫描会误伤台账引文**：初版全字段扫 `--apply/--approve`，把台账里**引用原文**的命令判成「越权动作语」（假警报）。改为两段口径——全字段只扫「动作完成声明」，CLI flag 只扫本工具自撰的「复核命令」区；并加一对负控 NC8（命令区 `--approve` 必报）/NC8b（引文里的 `--apply` 不报）。
4. **`note` 兼两职**：`premise_recheck` 的 note 在非 ACTIVE 时是**拒绝理由**而非收益 ⇒ 只有 `verdict=ACTIVE` 才输出「批了得到」，否则会把拒绝理由读成收益。
5. `view_pending.py --id <X>` 的输出=文件级统计表 + **末行**该条 ⇒ 只看头部会误判「没生效」（本轮白跑一轮）。
