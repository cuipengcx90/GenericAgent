## 2. 实现要点

1. **七个写命令**：`open`（开目标）/`add-item`（加条目）/`dispatch`、`dispatch-batch`（派单）/`working`（进执行）/`complete`（结清）/`escalate`（升人）/`resolve`（解升级）。
2. **跨轮不丢**：全部状态由 `goal.jsonl` **journal 派生**（read-side 重放），不依赖进程内状态 ⇒ 执行器进程死了、换 shell、隔夜再起，`resume` 读出的目标状态一致。
3. **fail-closed 升级闸门**：`escalate` 的三要素（卡在哪 / 试过什么 / 需要谁定什么）缺一即 rc=2 且**零写入**——不允许「沉默等人」。
4. **同 id 重放守卫（本轮新增的关键难点）**：
   - 同 id **同内容**重放 ⇒ 幂等 rc=0 且零写入（重跑不污染 journal）；
   - 同 id **异内容**重放 ⇒ rc=1 明确拒绝（防「悄悄改写历史升级请求」）；
   - 已 `resolve` 结清的升级 **不被重放复活**。
5. **产物 schema 对齐**：`goal.jsonl` / `NEEDS_HUMAN.md` / `alerts.json` 的告警条目与 `board.py`（看板警示区投影）、`alert_pipe.py`（R474 的 alert 消费者）同 schema ⇒ 无需适配层即可被消费。

## 4. 坑（可复用）

1. `tools/bg_task.py start` 的 `--name` **必填**，`status` 也用 `--name`（不是位置参数）；否则报 usage 而非任务状态。本机 `setsid` 不存在，RULES#15 的老配方不适用。
2. 全仓 `run_tests.sh` 会**改写受跟踪文件**（`acceptance_v1/runs/*.json` ×4）⇒ 提交前必须 `git status` 复核，绝不提交这些副产品。
3. `goal_loop.py escalate` **不接受 `--goal-id`**，参数名是 `--reason-kind/--where-stuck/--tried/--decision-needed/--option/--evidence-ref`；按直觉写 flag 会得到 usage 错（本次连踩两次，最后靠读 argparse 定义解决）。
4. 规格文档里的行数/字节/sha 须**回填后再复算**：改完 F11 正文，数值本身会变 ⇒ 表内 sha 与行数一律在最后一次编辑后重新取。
5. 提交信息含多行时用 `git commit -F <file>`；用 `repr()` 拼 `-m` 会把 `\n` 当字面量写进消息（本次首提交 `eeb3f61` 即此错，已 `--amend` 为 `fcecb0e`）。
