# R423 | Chrome 90 天历史快照首份消费（离线复算）

> 纯数据报告，**无任何外部来源引文**；全部数值由 `tools/chrome_history_consume.py` 于本机现场复算，可逐条重跑复核。

## 0. 一句话结论

R415 采下的唯一一份 Chrome 历史快照（2026-09-25）此前**零消费者**；本报告用新写的只读消费器（自测 13/13）把它跑成四类决策输入（备份 / 清理 / 定时任务择时 / 采集面），并量出一个此前无人知道的采集缺口：Default profile 之外本机还有 9 个 Chrome profile 未被采，占全机访问 8.6%（口径见 §3.6）。

## 2. 与 R392 的分工（验收②：只做未覆盖维度）

### 3.7 口径订正：副本字节数 ≠ 数据量

副本 History **16031744 B**，而同一时刻源库为 **33226752 B**（2.07 倍），但两者 visits 行数几乎相同（副本 30403 / 源库 30408）。原因是快照 manifest 记的采集方式为 `raw-file-copy+rollback+vacuum-into` —— 产物是 **VACUUM INTO 出来的压实单文件**。

**消费决策**：任何以快照文件字节为判据的新鲜度阈值、体量趋势或去重逻辑都不可与源库字节直接比较。**动作**：在消费/审计类工具里，源侧体量一律取 manifest 的 `src_before.bytes`，产物侧取 `revisions[].bytes`，两者不混算。

## 5. 隐私边界与限制（验收④）

- **不连网、不外发**：全流程本地只读计算，无网络请求；结果只落在本机 `temp/`（`.gitignore` 覆盖，不进仓库）。
- 报告与 JSON 内含具体域名与访问次数，属本机敏感的个人浏览轨迹 ⇒ 仅供本机消费；对外引用须先脱敏。
- 限制：①盘上**只有 09-25 一份** Chrome 快照 ⇒ 本报告是单时点截面，跨日增量要等快照累积；②只有 Default 一个 profile（见 §3.6）；③30/90 窗口的日均按日历天归一，月初月末天数不同会影响绝对值；④自驾判据的活跃比/CV 阈值为硬编码，只作提示；⑤Chrome 的 visits 表**不含停留时长** ⇒ 不能用它推使用时长，只能用访问次数；⑥`chrome-extension/file/blob` 行（305 条）未纳入统计。
