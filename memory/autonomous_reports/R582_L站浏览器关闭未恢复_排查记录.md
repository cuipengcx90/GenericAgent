## 3. 冷启动链的两个硬闸门(读码实证)

#
## 3.1 链路触发点:只有 `pick_session` 失败才补
`tools/linuxdo_browse_daemon.py` 主循环:
```
2422:  session, note = pick_session()
2424:      _ok, _note = try_ensure_tab()      # 仅上一行取不到会话时
2428:      session, note = pick_session()
```
⇒ 若 `pick_session()` 能拿到任一 linux.do 标签,`try_ensure_tab` **根本不会被调用**。

#
## 3.2 `try_ensure_tab` 的两个(且唯一)补标签路径
`tools/linuxdo_browse_daemon.py:2055` 起,AppleScript:
```applescript
if (count of windows) = 0 then make new window
...
tell window 1 to make new tab with properties {URL:"https://linux.do/"}
```
- **闸门 A(窗口/进程）**:AppleScript 只对**已存在的窗口**建标签;`count of windows = 0` 时才 `make new window`。**本步骤兼具冷启动能力**:若 Chrome 进程不存在,`tell application "Google Chrome"` 会先把它启动(AppleScript 对未运行的可脚本化 app 有冷启动语义,§3.3 已实证)。**但**这一切依赖 Automation(TCC)授权;10-10 两条台账即 `-1743 未获得授权` ⇒ **整个 AppleScript 路径(含冷启动)被拒绝**。
- **闸门 B(桥兜底也需已有会话)**:`-1743` 时改走 `_try_bridge_open_main_tab()`(纯 JS `window.open`),在**扩展已连上的某个标签**里执行。Chrome 若整体不存在,扩展无连接 ⇒ 函数返回 `"BRIDGE_OPEN 无可用会话(window.open 无处可发)"`,**无法建窗口**。

**关键订正(2026-10-13 加测后)**:初稿据此判"全仓无 `open -a` ⇒ 无稳定冷启动路径",**表述过强、已被推翻**。正确结论是:**冷启动路径本就在 AppleScript 里(`make new window`),它的开关是 TCC Automation 授权**——
- 授权**在** ⇒ AppleScript 会冷启动 Chrome 并建窗,链路通(即 R556 当初真机验证的场景);
- 授权**丢**(-1743) ⇒ AppleScript 整条路径(含冷启动)被拒,此时**只有桥兜底**,而桥兜底**必须有现存会话** ⇒ 若同时"Chrome 已整体退出",两路俱灭 = 真的无法拉起。
⇒ 缺口不是"缺 `open -a` 命令",而是**在授权缺失 + 无现存会话时缺一个不依赖 TCC 的兜底**(如 `open -a "Google Chrome" <url>`,`open` 属 LaunchServices、不经 Apple Events,故不受 -1743 影响)。watchd 亦只探 daemon 心跳与桥,不探 Chrome 进程。

## 3.3 加测实证:AppleScript 能冷启动"未运行"的 app(2026-10-13,无害替身)
为验证"AppleScript 是否会冷启动一个不在运行的 app"(不拿 Chrome 做实验),选无害可脚本化 app `TextEdit`(实验前 `pgrep -x TextEdit` = 未运行):
```
# 实验1:activate
$ osascript -e 'tell application "TextEdit" to activate'     => rc=0
$ pgrep -x TextEdit                                          => 已运行, pid=8252   ← 被冷启动
# 实验2(同 Chrome "make new window" 类比):直接发建文档事件
$ osascript -e 'tell application "TextEdit" to make new document' => rc=0, out="document 未命名2"
$ pgrep -x TextEdit                                          => 已运行, pid=19142  ← 被冷启动
# 清理
$ osascript -e 'tell application "TextEdit" to quit saving no' => rc=0
$ pgrep -x TextEdit                                          => 未运行
```
⇒ **AppleScript 对未运行的目标 app 会先启动它再执行事件**(前提:TCC 允许向该 app 发 Apple Events)。这正对应守护里 `tell application "Google Chrome" … make new window`:**授权在时,Chrome 未运行也会被拉起**;10-10 的 `-1743` 则是"授权不在"导致连启动带事件一起被拒。注:`activate` 与 `make new document` 两条都冷启动成功,说明这是 AppleScript/Apple Event 的通用语义,而非某条命令的特例。

## 6. 建议(需用户裁决,涉及改 GA 源码)

按"浏览器真被关掉"的目标场景,现状的**缺口**=**当 Automation 授权缺失(-1743)且无现存会话时,没有任何可拉起 Chrome 的路径**(AppleScript 被授权拒、桥需现存会话)。订正后的处置:

- **A(最小/推荐,补"非 TCC 兜底"）**:在 `try_ensure_tab` 的 AppleScript 与桥两路都未能建标签时,补一档 `open -a "Google Chrome" https://linux.do/`(`open` 走 LaunchServices、**不经 Apple Events,故不受 -1743 影响**)。它既能在"Chrome 进程不存在"时拉起,也天然带出主站标签。仍受"日上限6次/间隔10min"闸门约束。改动小、语义明确、**不依赖任何系统授权**。
- **B**:给 watchd 增一条 **Chrome 进程探针**(`pgrep -x "Google Chrome"`);进程不在且非静默窗 ⇒ 拉起 Chrome(与 daemon 探活同级)。使守护能看见"浏览器层"故障。
- **C**:恢复/固化 Automation 授权(让 `-1743` 不再复发)——能恢复则 AppleScript 冷启动链重新可用;但这是**系统授权**、且可能被系统更新重置,不能作为唯一致胜手段,应与 A/B 组合。

> 以上均为**改 GA 源码/系统行为**,按 Constitution 第1条需用户先批;本报告只做诊断,未落任何代码改动。
