命中率 2/8 = 25%，且命中处都是 thinking/tool_result **片段**（正文分散在多轮），无法逐字节重建 ⇒ **L4 只能做交叉取证，不能当 L2 的恢复源**。

**为什么仍选 C（即使 B 更省）**：
1. 份数上限 30（§4 策略）⇒ C 的上限 ≈ 2.2 MB，对 13 GiB 可用空间无实质影响；成本差异不在同一个数量级的问题上。

## 3. 工具设计（`tools/l2_snapshot.py`，新文件）

```
snapshot --file <路径…> [--label 文本] [--store DIR]
list --store DIR
verify --store DIR                     # 逐条重算 sha256 比对台账
restore --file <路径> --out <目标>      # 必须给 --out；就地回滚须 --allow-in-place
prune [--apply]                        # 默认 dry-run
policy --store DIR                     # 保留策略机械校验（见下）
selftest
```

- **对象层**：`objects/<sha256>.gz`，gzip level 9。内容寻址 ⇒ 相同内容自动复用（同内容第二次快照输出 `SKIP`，写 0 字节）。
- **台账层**：`manifest.jsonl`，append-only，字段 `path / ts / sha256 / size / label / kind`。
- **默认 store**：`~/.ga/l2_snapshots`（仓外、不随 repo 被清、不进 git）。
- **恢复后自动入账**：`restore` 写目标文件后，若目标是**受管文件**或显式 `--record`，则把"回滚后内容"作为新版本入账（幂等；因对象复用，磁盘增量为 0）。这一步是为了堵审计盲点：回滚后 L2 与台账最新版本不一致，会让"最新版本"这个判据静默骗人。
- **保留策略（写死，可机械校验）**：
  - 每路径 ≤ **30 份**（超出时 `prune` 按时间从旧到新删）
  - store 总占用 ≤ **64 MiB**
  - 每路径至少 1 份
  - 保留版本的 gzip 对象必须齐备（无缺失）
  - 不得存在孤儿对象（未被任何保留条目引用的对象）
  - manifest 无坏行

## 5. 本轮自曝缺陷与修复（最有价值的一条）

**⑥ 自测首次 FAIL：`台账 2 → 3 → 4`（幂等守卫没生效）。**

根因（读源码 + 最小复现定位）：取"最新版本"的函数按 `(ts, sha256)` 排序取末位——

```python
cand.sort(key=lambda e: (e.get("ts",""), e.get("sha256","")))
return cand[-1]
```

同一秒内的多条记录 `ts` 相同，就退化成**按 sha256 字典序取"最大"**，于是"最新版本"实际上是"sha 最大的那个旧版本"，幂等判断拿到了错的基准。

修法：改为按 **`(ts, 台账插入序)`** 定序（台账是 append-only，插入序即时间序的真实来源），并对所有"取最新"的调用点统一走同一个 `ordered()`。

**教训（可推广）**：任何"取最新/取末条"的判据，**时间戳相同的情况下必须有第二判据**（插入序/序号），否则会静默取错——这类错误不会报错、只会让幂等与审计判据悄悄失效（与本仓库既有教训同源：判据错了比没有判据更危险）。

另外两处本会话修掉的小问题：`restore` 桩对象缺新字段导致 `AttributeError`（改用 `getattr` 兼容）；`--out` 从可选改必填 + 就地回滚需显式 `--allow-in-place`（防误覆盖真文件）。
