## 1. 做了什么（一句话）

把既有证据（`autonomy_v0` run 落账 + `kpi_report` + 人工干预台账）汇成**按「夜批」聚合的
append-only 账本**，并用三条**可判定字面规则**（R1–R3）判「这一夜人被打断了几次」，
从而给出每夜的**无人干预率**；装置**被迫叫人/降级**（R4）另立一格，**互不吞并**。

本批**只做「记录器 + 判据 + 一个真实回放数值」**，不承诺 7 天连续达标、不新增调度器
（这两条来自 TODO 的收窄条件，见 §9）。

## 2. 为什么会有这条任务：阶段四验收缺一个「能连续记录的东西」

阶段四验收明文要求「**连续 7 天夜批 ≥80% 无人工干预**」。但在本批之前：

| 现状 | 证据 |
|---|---|
| 没有任何组件在记录「每夜人被打断几次/多久」 | `R435` 架构剩余工作量总账把该口径列为 P2 |
| KPI 只有一个计数格、没有时间轴 | `kpi_report` 的 `human_interventions` 单格 |
| 口径扩展本身是「待建」 | `docs/product/FUTURE_CAPABILITIES.md` §14 |

也就是说：**验收的分母/分子此前无人产出**，先得把「能连续记录的东西」做出来。

## 3. 判据：谁、在什么条件下算「干预」

规格 `docs/product/F8_UNATTENDED_NIGHT_LEDGER_SPEC.md` §2 把干预定义落成字面规则：

| 规则 | 条件（字面） | 数据来源 |
|---|---|---|
| **R1** | 该 run 的 `kpi.human_interventions` > 0 | run 记录里的 KPI 快照 |
| **R2** | 该 run 的 history 里出现 `actor=human` 的推进/裁决事件 | run 状态机 history |
| **R3** | 该 run 命中**人工干预台账**里的记录（`log-intervention` 落的行） | 主台账 / `--interventions` 台账 |

三态叠加：**任一命中 ⇒ 该 run 记「被干预」；该 night 只要有一个 run 被干预 ⇒ 该夜记「有干预」**。
无人干预率两条口径都给：

- 按夜批：`1 − 被干预夜数 / 总夜数`
- 按 run：`1 − 被干预 run 数 / 总 run 数`

**另一格（不并入上面）**：**R4 = 装置被迫叫人/降级**（`ESCALATED` 等），单列一格。
这条是 FUTURE §14 的判据本身：**人的显式干预 ≠ 装置的被迫降级**，混在一起算就是口径污染。
负控已固化：把 R4 混进干预计数 ⇒ `selftest` 必红。

```

**五个**子命令（**位置参数**，不是 `--flag`）：

| 子命令 | 行为 |
|---|---|
| `replay` | 只读回放：按夜聚合当前语料的 run/干预，直接打表或 `--json` |
| `append` | 把当前语料的夜记录**幂等**追加进台账 |
| `report` | 只读：从台账出「每夜最后一条 + 无人干预率」 |
| `log-intervention` | 记一次人工干预（append-only），支持 `--at/--by/--run-id/--kind/--note/--night/--id` |
| `selftest` | 断言 + 负控 |

（`replay/append` 通过 `common(p)` 共用 `--runs-root/--all/--day-boundary-hour/--interventions/--ledger`；
单夜的构建是**内部函数** `build_night()`，不是 CLI 子命令。`--ledger` 不设默认路径以免误写进仓，
`report`/`log-intervention` 在 argparse 层 `required=True`。）

三条纪律（模块 docstring §「三条纪律」，与 `collector.py` 同源）：

1. **逐条可复算**：每个数字都从账本重算；算不出写 `null`，**绝不写 0**。
2. **不吞并**：R1–R3（人的显式干预）与 R4（装置被迫叫人/降级）两格。
3. **追加即历史**：同输入重跑 ⇒ 同 `ledger_id` ⇒ **跳过不重号**；输入变了 ⇒ 追加新版本；
   `report` 只认每夜**最后一条**。

「不重号」怎么保证：`ledger_id_for_night(night, boundary_hour, run_ids, intervention_ids)` ——
即 `ledger_id` 由**夜 + 边界小时 + 该夜涉及的全部 run id 与干预 id** 派生；
`append_jsonl` 先读台账已有 `ledger_id`/`id` 集合，命中即跳过。模块定义三个 schema 常量
（`SCHEMA_NIGHT = ga.unattended-night/v1` / `SCHEMA_INTERVENTION = ga.unattended-intervention/v1` /
`SCHEMA_REPORT = ga.unattended-report/v1`）。

另一格（FUTURE §14，不并入上面）：被迫叫人/降级 runs=9
```

**口径说明（必读，否则会误读这张表）**：

- **只有 2025-09-16 那一夜被判「有干预」**（R1 命中 1、R2 命中 1），其余 7 夜干预=0。
  因此 0.875 是「过去语料里 8 夜中 7 夜没人碰」的**历史回放值**，
  **不是**「连续 7 天达标」的证据（那要真跑够 7 天，见 §9）。
- **`被迫=9` 不并入**无人干预率的分子：8 条来自 2026-09-22（`ESCALATED` 8），
  1 条来自 2025-09-16。这一夜正是「装置被迫降级 ≠ 人动手」的现场样本：
  2026-09-22 被迫 8 次但**人工干预 0**——如果两格合并，就会把「自动降级」误报成「人被打断」。
- `墙钟总` 单位是秒，取自 `collector` 的墙钟派生（本器**不重写**第二套口径）。
- `无首 ts：0` 表示没有 run 因缺首时间戳被丢弃；这类记录会进 `runs_undated` 而**不静默丢**
  （`selftest` 里有专门断言：「PASS 无 ts 的记录进 runs_undated（不静默丢）」）。
