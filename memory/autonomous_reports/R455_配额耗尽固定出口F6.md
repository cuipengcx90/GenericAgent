## 2. 契约：原因四元组

| 字段 | 含义 | 取值（白名单） |
|---|---|---|
| `limit_key` | **哪条 limit** 拦的 | `max_members` / `max_parallel_by_kind` / `max_replacements` |
| `limit_value` | 声明的上限 | 整数 |
| `actual` | 实际值 | 整数 |
| `scope` | 在哪条路径上被拦 | `launch` / `replace` / `drive` |

旧字段 `requested` / `limit` **保留不删**（E4 已公布的形状，删掉会破既有读者）；只有旧字段的记录
在断言器里报 `LEGACY_FIELDS`。

**两层口径刻意分开**（免得把没实现的东西画成已实现）：
`ENFORCED_LIMIT_KEYS = ("max_members",)` 是现役**真会拒**的唯一一条；
`KNOWN_LIMIT_KEYS` 多出的两个键出现在留痕里**不是错误**，只给提示 `DECLARATION_ONLY_KEY`。

## 3. 判据与退出码

断言器对一棵团队目录 `--team-dir D` 审：账本存在且行可解析 → 存在 `CONCURRENCY_EXCEEDED` 记录
→ 每条带全 `REQUIRED_FIELDS=(kind, scope, limit_key, limit_value, actual, at)` → `limit_key`/`scope`
在白名单内 → `actual > limit_value` → 与 `workflow-state.json` 的 `limits` 声明对得上。

- 违例码（`rc=1`）：`NO_EXIT_RECORDED`、`LEDGER_MISSING`、`BAD_JSON_LINE`、`FIELD_MISSING`、
  `LEGACY_FIELDS`、`UNKNOWN_LIMIT_KEY`、`UNKNOWN_SCOPE`、`VALUE_NOT_INT`、`NOT_EXCEEDED`、
  `LIMIT_MISMATCH`、`AT_TYPE`
- 提示码（不影响退出码）：`LIMITS_UNDECLARED_SEEN`、`ABSENT_ALLOWED`、`DECLARATION_ONLY_KEY`
- 退出码：通过 `0` / 违例 `1` / 用法错误或 fail-closed `2`（`--team-dir` 非目录）
- JSON：`schema = ga.quota-exit/v1`

`--allow-absent` 的边界是刻意的：它放行「账本在、但一条超限都没有」（`rc=0` + `ABSENT_ALLOWED`），
**不放行账本文件不存在**（仍 `rc=1` `LEDGER_MISSING`）——「没超限」是状态，「没读到」是读失败，
放行后者等于用一个空目录换一张合格证明。
