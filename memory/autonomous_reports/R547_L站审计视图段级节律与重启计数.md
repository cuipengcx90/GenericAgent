## 1 #5 段级节律视图（`daemon status` → `segments`）

以前只有「今日浏览 N 帖 / 等级缺几项」，看不出**节律是否按设计走**。现在 `status` 直接把当日段计划与既成事实并列：
它的取值来自**内核单一源** `tools/linuxdo_antidetect.py` 的 `day_segments(day, kind)`（日期种子派生，重启不改），与 daemon 实际记账的 `browse_log` 对账：

- `theoretical` 4 = 今日计划段数；`segments_seen` 1 + `segments_seen_idx` [1] = 实际已进入并消费过的段；`browsed_in_segment` 4 = 当前段内已消费帖数；`current_window` [11:03, 11:59, 56.3] = 当前段起止与剩余分钟。
- `rests` / `rests_n` 1 / `rests_long_n` 1 / 长休明细 `00:11→11:17, 666.4min, long=true`：**这就是 R546 修复①的直接证据面**——段位改由日期种子派生后，长休（跨静默窗的段间空档）第一次在视图里可见；修复前重启会把段计时清零，全天从不出现长休。
- 同时并列 `daily_browsed` 7 / `total` 109 / `level {met 11, pending 1}`，与等级缺项路由同屏判读。

## 2 #7 重启计数视图（`watchd status` → `restarts`）

真跑输出（2026-10-06 11:49）：

- `restarts_total` 42 / `restarts_today` 41 / `restarts_ok` 4 / `restarts_failed` 38 / `restarts_last_hour` 4 / `rate_limit_per_hour` 3。
- `last_restart {ts 11:14:01, reason STALLED_39527s, ok false}`、`last_start 11:22:43`、`daemon_started 11:13:57`（daemon pid 58220、watchd pid 81824）。
判读（这张视图让 R546 的效果第一次可量化）：42 次重启里 **41 次集中在今天**、且 `last_restart` 停在 **11:14:01**，而 R546 新码起队时刻 `daemon_started` = 11:13:57 ⇒ 修复后的重启只剩风暴尾巴那一次（`STALLED_39527s` 正是 R546 报告里点名的「起队后 4s 冷启动误杀」），**11:14:01 之后至今约 36 分钟零重启**；`restarts_last_hour` 4 > `rate_limit_per_hour` 3 同样只是近一小时窗口仍含风暴尾部，不是新发风暴。

口径两条（写进 SOP §9.1）：

1. 段级视图只统计**当日**、只认 `DONE` 行的**真实时间戳**（非 DONE / 坏时间戳 / 昨天的行一律不计）。
2. `restarts_ok`（真把子进程拉起来）与 `restarts_failed`（如 `HOLD_BUSY` 让位）**分列**——`restarts_failed` 是判据档不是异常档：41/4 这种失败率恰是风暴证据，修好后该值应停止增长。

## 5 残余与边界

1. 视图是**事后审计**：它让风暴/长休可测可量化，但不阻止风暴——阻止靠 R546 的多源停滞判据 + `BLOCKED_ENV`。
2. `rate_limit_per_hour` 仍是**观测阈值**（超了只打印），未接自动熔断；是否升级为硬闸门属政策取舍（须批量重建/重启策略），留待用户拍板。
3. 两件视图**未接任何定时任务**（守「禁固定时刻」铁律），只在人工排查或 daemon/watchd 自身日志里使用。
4. 段级视图分母是内核当日段计划；若当日跨静默窗或风控暂停导致段未消费，视图如实显示 `segments_seen < theoretical`，**不补零、不美化成达标**。
