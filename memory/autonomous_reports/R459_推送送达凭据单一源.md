## 4. 核心发现：`claim_conflict`（自述与代码路径相反）

全仓命中 **2 条**（`flags=claim_conflict`，均 PUSHED）：

| 文件 | 剖面 | 判定 |
|---|---|---|
| `2026-08-03_1101_birdie_daily_monitor.md` | birdie | PUSHED(guard_infer) + claim_conflict |
| `2026-08-07_1100_birdie_daily_monitor.md` | birdie | PUSHED(guard_infer) + claim_conflict |

> 首版判据曾命中 5 条（多出 `2026-08-23` / `2026-08-30` / `2026-09-21` 三份 haisou），复核后判定为**假阳性**：那三份报告的自述是「本会话未额外补推」——它只否认**补推**这件事，并不否认脚本自己推送过，与 `guard_infer` 结论并不矛盾。据此把冲突判据收窄为「**否定推送本身**」（`未触发…(推送|通知)` / `未推送` / `未发送` / `推送次数…0`），而 `未额外` 仍保留在证据收集用的 `NEG_CLAIM_PATTERNS` 里（它确实是自述，只是不该判冲突）。详见 §6 第 4 条。

08-03 原文（逐字，`sche_tasks/done/2026-08-03_1101_birdie_daily_monitor.md` 第 12、18 行）围栏内脚本输出 `⚠️ 今日搜索额度已用尽，提前停止。`，散文说明里写：

- 「今日无新增命中，脚本内部逻辑判定无需推送，未触发飞书私信/钉钉群通知，未额外调用其他通知函数。」

而护栏原文（`birdie_monitor/birdie_daily.py:125` 上下文）是：

```
    report = build_report(new_items, quota_hit)
    print(report)
    if new_items or quota_hit:
        notify(report)
```

即 **`quota_hit` 为真时 notify 必被调用** ⇒ 该报告的「未触发…通知」是对代码路径的误读。判定器据此确立铁律：

> **guard_infer（代码路径推导）优先于 prose claim（模型自述）；冲突不降级，只挂 flag 留痕**（`reason` 追加「⚠ 自述『未推送』与代码路径相反（判读以代码为准）」）。

**为什么不是「降级成不可判」**：一个能解释代码路径的判据，比一份会误读代码的散文自述更接近事实；把冲突降级会让所有这类文件重新落入「不可判」，等于把已知结论丢掉。留痕则保证后人一眼看见分歧点。

## 5. 三态语义与护栏（单一源口径）

| 态 | 条件 |
|---|---|
| `PUSHED` | ① 落盘凭据（state.json/tracker 指纹推进，`credential`）；或② **guard_infer**：脚本必有 notify 调用 ∧ **存在脚本输出围栏** ∧ 无失败标记 |
| `NOT_PUSHED` | 显式失败标记（两通道推送失败、exit≠0 等）；或 `prereq_abort`（前置失败、未到推送步骤） |
| `UNDETERMINABLE` | 无证据（`no_evidence`）、只有固定文案（`boilerplate_only`）、只有散文自述（`prose_claim_only`）、凭据未变（`state_unchanged`）、自述冲突但无代码路径证据 |

关键前提（本轮修正的坑）：**`guard_infer` 必须有「脚本输出围栏」**。早期版本在没有围栏的纯散文报告上也会推 PUSHED，属过度推断——现要求 `has_fenced`；`prose-claims` 默认 `advisory`（自述只作提示），`decisive` 档仅作对照开关。

**散文引文护栏**（本轮新增）：失败标记名出现在**散文**里时不等于真失败——报告常写「两通道**任一路异常必打印** `[飞书私信推送失败]`」这类机制说明，或「日志计数 `[钉钉群推送失败]` = **0**」这类零计数断言。判据：散文行的 `E_FAIL/E_PREREQ` 证据，若满足 ①含机制词（必打印/任一路/并非降级…）②或含零计数断言 ③或为反事实表述，则**不计失败证据**；真失败行（如「本轮共 3 次 [钉钉群推送失败]」）仍照判 NOT_PUSHED（NC21 反向守住）。

**否定自述分两层**（单一源，避免剖面重复写正则）：
- `NEG_CLAIM_PATTERNS` = `未触发.*(推送|通知)` / `未推送` / `未发送` / `未额外` ⇒ **证据收集**用（`collect` 并入 claim 扫描；四类都算「自述」）。
- `NEG_CLAIM_RE` = `未触发.*(推送|通知)` / `未推送` / `未发送` / `推送次数…0` ⇒ **冲突检测**用（去掉 `未额外`：它只否认补推，不否认推送本身）。

## 6. 计划外的四个坑（本轮实测，均已修）

1. **自述句被 `boilerplate` 吃掉 ⇒ claim 收集不到**：birdie 剖面 `boilerplate` 里有 `未触发飞书私信`，而 claim 侧只写了 `未触发.*推送`；当报告写「未触发飞书私信/钉钉群**通知**」时两边都不命中 ⇒ 冲突检测形同虚设（NC7 首跑即复现，`flags=[]`）。修法=抽 `NEG_CLAIM_PATTERNS` 共享并入 claim 扫描。
2. **修断言用词误伤**：首版改名脚本按字符串整段匹配带转义的正则文本，`assert count==1` 失败（实际 0）⇒ 改为 token 级替换并自证出现次数（2 处），避免转义地狱。
3. **散文里「引用失败标记名」被当成真失败**（真跑才暴露）：haisou 09-27 报告在散文里写「`notify()` 两通道**任一路异常必打印** `[飞书私信推送失败] …`」，判据原先只看「行内出现标记名」⇒ 把它判成 NOT_PUSHED，而该轮实际是**扫描中途 HTTP 403 提前停止**、脚本仍调了 notify。修法=§5「散文引文护栏」；修后 haisou 族 12 条 NOT_PUSHED→11、PUSHED 4→5（正是被误判的那条转正）。
4. **`未额外` 被当成「否认推送」**：`NEG_CLAIM_PATTERNS` 里的 `未额外`（「本会话未额外补推」）只否认**补推**，与「脚本自己推送过」不矛盾；它先被并入冲突检测，导致 haisou 三条报告被误挂 `claim_conflict`。修法=冲突检测改用收窄的 `NEG_CLAIM_RE`（保留 `未额外` 于证据收集），命中数 5→2。
