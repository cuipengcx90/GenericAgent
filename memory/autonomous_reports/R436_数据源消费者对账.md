## 1. 问题

`tools/usage_census.py`（R421）只判 **`tools/*.py` 的引用面**（谁被谁引用：实测 40 个 tools 里接线 18 / 仅记忆 18 / 仅报告 4 / 无引用 0）。
**数据源侧没有人做同一件事**——「我们采了一批数据，却没有任何消费者」这件事没有任何工具能回答。而它已经在真机反复发生：

- R423：R415 采的 Chrome 历史快照，采完才发现全仓零消费者（当天才写 `chrome_history_consume.py`）；
- R434：kc 的 `/app/usage`（10427 条）与 `/notification/usage`（5706 条）同样是「万级数据零消费者」，当天才被 `tools/kc_app_usage.py` 消费。

本器把这件事做成**可复跑的对账**：对一批**数据源**逐个回答「有料吗？谁在消费？首个消费者是谁？」，并输出「有料但零消费者」清单。
消费者（真正的下游价值）= 下一批规划选题依据：避免再造无人消费的工具/再去采无人消费的源。

## 3. 口径：谁算消费者（验收②）

按**引用该源的代码文件的角色**三分；角色登记在 `COLLECTORS` / `GUARDS_POLICY` 里，逐条给理由：

* **CONSUMER（消费者）** = 读取该源并产出**派生结论/指标**的模块
  （例：`tools/kc_app_usage.py`、`tools/sleep_source_crosscheck.py`、`tools/chrome_history_consume.py`）。
* **COLLECTOR（采集器）** = 只搬运/快照/拷贝，不产出派生结论（例：`tools/rolling_source_snapshot.py`）。
  采集器**不计**消费者：只搬运不算「有人用这份数据」。
* **GUARD / POLICY（守卫·策略）** = 只做健康判定，或把源名当白名单/地图
  （例：`tools/kc_snapshot_guard.py`、`tools/personal_source_map.py`、`tools/usage_census.py`）。
* 仅 durable 记忆 / 仅报告引用 ⇒ 记作参考面，**不计**消费者。

判定结论只有五种：`CONSUMED` / `COLLECTOR_ONLY` / `GUARD_ONLY` / `REF_ONLY` / `NONE`。
**只有 `CONSUMED` 算「有消费者」**；后四种都算「实质零消费者」，其中 `COLLECTOR_ONLY` / `GUARD_ONLY` 属**弱消费**（有人在读，但没产出结论），单列不混入主清单。

范围：在册源 = kc 三流（`/app/usage`、`/notification/usage`、`/display/isBacklit`）+ **全部带 `History` 的 Chrome profile**（真机 Default + 9 个非 Default，见 §5）。
**附节**（`scope="kc-other"`）= 同一 kc 快照里的其余流（`/app/mediaUsage`、`/bluetooth/isConnected`、`/discoverability/signals`），同法判定；它们是 kc 源内部的细分，**不引入** `personal_source_map` 的 12 个外部源（即：本器没有做 12 源普查，验收②要求的收窄已遵守）。

### 3.1 动态消费者（token 检索测不到的引用）

`chrome:Profile N` 这类源，profile **名不进源码字面量**：`tools/chrome_profiles_consume.py` 用 `discover_profiles()` 枚举目录，所以对 profile 名做 token 检索必然 0 命中——若不管，10 个 profile 会被全判「零消费者」= 假警报刷屏。处理办法：

```python
DYNAMIC_CONSUMERS = {
    "chrome:*": [
        {"path": "tools/chrome_profiles_consume.py", "probe": "discover_profiles",
         "why": "R430：按 discover_profiles() 枚举全部 profile，profile 名不进源码字面量"},
    ],
}
```

* 每条登记**必须给可机械验证的探针**（`probe` = 必须出现在该文件里的字符串）；探针失效或文件不存在 ⇒ **fail-closed**，不计消费者（宁可报「零消费者」，不可凭空认亲）。
* 命中记 `DYNAMIC_CONSUMED` 且 `first_consumer` = 该文件。

### 3.2 只读（验收④）

* kc 快照副本走 `file:...?mode=ro`；
* Chrome **源库一律只做 sha256**，任何 SQL 都跑在 `chrome_profiles_consume` 拷贝出的工作区副本上；
* `--readonly-proof` 打印源侧指纹前后一致自证。

## 8. 坑（本次实测踩到的）

1. **`--no-profiles` 会让负控恒报违例**：该模式下 Chrome 面整面缺席，而 `KNOWN_CONSUMED` 里 2 条是 Chrome 源 ⇒ guard 判「源缺失」抬 rc=2。但当过 `--no-profiles` 是**合法模式**，不是数据问题。修法 = 该模式把负控范围收窄到 kc 侧登记并在输出里显式声明（`[负控范围] --no-profiles ⇒ 只在册 1 条 kc 侧登记做负控`）。**教训：负控清单要跟着模式收窄，否则负控自己变成噪音源。**
2. **登记面扩了、自测断言没同步**：`KNOWN_CONSUMED` 从 1 条扩到 3 条后，旧的 NC2/NC3/NC4 断言（按 1 条写死）立刻失败——工具本身是对的，是测试过期。**教训：负控断言里凡出现「条数」必写成从登记表推导，不能写死常量。**
3. **guard 必须把动态消费者视同在场**：`chrome:Profile 3` 走的是动态登记（token 检索 0 命中），guard 若只查 token 命中就会把自己刚认下的源判成「源缺失」。修法 = guard 同时接受 `dynamic_consumers`（自测 T13/NC10 覆盖「动态那路缺失必报」）。
4. 小坑两条（读实现核对，防误读）：①`--json` 的 `default=None` ⇒ **不给路径就不落盘**，docstring 第 51 行示例里的 `temp/source_census/<date>.json` 只是给人照抄的示例路径（真跑用的是 `temp/source_consumer_census/`）；②真跑输出里「采集器/守卫/记忆/报告/动态」五列是**命中个数**（`len(collectors)`/`len(guards)`/`mem_hits`/`report_hits`/`len(dynamic_consumers)`），不是角色布尔值——勿误读成「有/无」。

## 9. 边界与未接线

* **范围**：16 个在册源 = kc（3 主流 + 3 附节流）+ 10 个 Chrome profile；**不是** 12 源普查（`personal_source_map` 的 12 个外部源里，Messages/Mail/Photos 等空库源未纳入）。
* **消费者判据是「源码/记忆/报告里的引用」**，不是运行时行为：一个模块引用了源但从不被调度，本器仍记它「消费」——调度面归 `tools/task_freshness.py`（R411）管，两者互补。
* **未接线**：没有接 `complete_task` 收尾、也没有定时/反射器；当前是手动复跑工具（真跑 <2s，成本可忽略）。
* kc 面结论**只用 2026-09-25 快照**（kc 有迟写回填，见 L2 口径铁律）⇒ 行数/有料判定随快照时点变。
