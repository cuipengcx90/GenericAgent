# R570 周报「本周」窗口改按首个工作日 + 解释器自愈(生产环境根因)

日期: 2026-10-10 | 类型: 修复 | 触发: 用户「今天的周报为什么显示10月5号?我让你算的是工作日」

## 1. 用户诉求与边界
- 用户明确: **本次邮件不需要改**,只要求**后续工作日计算逻辑正确**。
- 因此本批只修「计算/调度链路 + 文档口径」,不动已发出的草稿。

## 2. 两个根因(第二层才是要害)
### R1 口径层(表层)
`temp/get_week_range.py` 旧实现硬编码 `exec_date - timedelta(days=weekday())` 取**自然周一**,
与 SOP / reflect scheduler 的「本周第一个工作日」口径**自相矛盾**。
国庆假后 10-10(周五)该式给出 10-05(周六,假日)⇒ 主题/intro 写成 `2026.10.05 - 2026.10.10`。

### R2 环境层(真根因,决定性)
该脚本设计为调 `chinese_calendar.is_workday` 排除节假日,但:
- 生产与会话 agent 执行 code_run 用的都是 **Galley 内置 python3.11**(实测 `sys.executable` =
  `/Applications/Galley.app/Contents/Resources/python/bin/python3`),**无 chinese_calendar**;
- 系统 `/usr/bin/python3`(CommandLineTools 3.9)**也无**该库;
- 仅 `/opt/anaconda3/bin/python3` 有。

⇒ 生产环境下 `_load_workday()` 恒失败,脚本**静默降级**为自然周一 = 10-05。
**结论: 只改口径不解决问题——必须做「解释器自愈」**,否则改完仍是 10-05。## 3. 修复内容

## 7. 可复用教训
- **「口径改对」≠「结果改对」**: 先验证**生产者实际执行环境**(`sys.executable` 及其已装库),
  再谈口径;本次若只改算法,生产仍输出 10-05。
- 依赖外部库的确定性脚本,在不可控解释器环境下应**自带解释器自愈**,并在降级时**显式打标**
  (禁止静默降级——静默降级正是本事故被隐藏多期(08-28 起)的原因)。
- 改共享长行文件(SOP/索引)提交前按 blob/JSON 结构化比对**分离他会话改动**,以 numstat 逐项核归属。
