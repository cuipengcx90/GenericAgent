# R369 检索式回忆最小实证：FTS5 是否值得固化

日期：2026-09-23  | 任务：TODO#53  | 约束：只读语料；索引、测量和报告均在 `temp/`；不写 `memory/`。

## 0. 结论

**结论：不把本轮索引直接固化为生产工具；把「检索式回忆」保留为可复用的 temp 原型。**

理由不是检索没价值，而是原型的价值边界很清楚：

- 有索引的人工拆词查询 top-5 命中 7/12，自动三元组查询 8/12；单题查询 0.1–3.3 ms。
- 无索引每题扫描 37.79 MB、耗时 0.101 s，但筛出 73.9 个命中文件、仍需阅读 5.67 MB（约 188.9 万粗 token）。
- 所以**定位成本有明确收益**；但原型仍有查询构造与排序问题：整句短语会直接 0 行，top-5 漏报是排序截断而非语料缺失（12/12 题的目标块都在任一模式的 top-50 内）。
- 建索引**不改变每轮注入面**：当前只注入 L1 摘要，索引改善的是按需定位，不会自动多注入上下文。

若后续接入，最低要求是：查询先拆词（禁整句短语）、证据级重排与去重、返回带路径与行号、索引新鲜度可检测，并继续保持语料只读和状态隔离在 temp。

## 2. 实验范围与口径

### 2.1 语料与索引（本次快照）

语料枚举 1,247 个文件、37.80 MB 文本（`memory/` 递归 242、`temp/autonomous_reports/` 35、`temp/pending_decisions/` 56、`tools/` 15、`reflect_scripts/` 16、`sche_tasks/` 37、`temp/` 顶层 846），切为 14,000 个 chunks；其中 10 个文件为空或过短，未产出 chunk，故库里 distinct path 为 1,237。索引格式 SQLite FTS5 trigram；构建 5.02 s（脚本内计时，墙钟 6.27 s），库体积 152,895,488 字节（145.8 MiB）。索引位于 `temp/recall_probe/index.db`，不是生产索引。

⚠️ 语料枚举包含 `temp/` 顶层脚本与 `temp/` 下报告/决策目录，**会随 temp 变动而漂移**，因此文中所有数字标注为拍摄时刻快照；本报告文件本身写入 `temp/autonomous_reports/` 会让文档数再 +1。

### 2.2 三种有索引查询

- `whole_q`：整句问题作为一个 FTS 短语查询。
- `kw`：人工关键词集合，每题 2–3 个词，OR 查询。
- `auto`：从问题自动抽 ASCII 词与中文三字片段，最多 80 个词，OR 查询。

判中口径严格：top-k 中需存在某 chunk，其文件 == gold 且 chunk 文本含该题 probe 子串。该口径下 12/12 题的目标块都在**任一模式 top-50 内**（按单模式看：`kw` 为 12/12、`auto` 为 11/12；唯一例外是 Q4 的 `auto`，要放到 124 位才命中；若收紧到 top-10，两模式各为 9/12）。也就是说 top-5 的漏报主要是排序/截断，不能读作「语料不可检索」。

粗 token 统一按 UTF-8 字节 / 3.0 估算，仅用于同口径相对比较，不代表任何模型真实 tokenizer。

### 2.3 无索引基线

每题用自己的人工关键词集合扫描全语料，记录扫描字节、命中文件数、命中文件需阅读字节与耗时；**按题独立测量**，不复用缓存。另有一次真实 `grep -rl` 参考扫描（单关键词，仅 memory + reports），耗时 0.07 s，与 Python 基线同量级。

## 3. 真数（快照）

### 3.1 有索引三模式（12 题平均）

| 模式 | hit@1 | hit@3 | hit@5 | 返回字节 | 粗 token | 查询耗时 |
|---|---:|---:|---:|---:|---:|---:|
| `whole_q` 整句短语 | 0/12 | 0/12 | 0/12 | 0.2 KB | 68 | 0.1 ms |
| `kw` 人工拆词 | 5/12 | 7/12 | 7/12 | 11.2 KB | 3,734 | 0.5 ms |
| `auto` 自动三元组 | 5/12 | 6/12 | 8/12 | 9.2 KB | 3,064 | 3.3 ms |

`whole_q` 的 hit@5 为 0 不是「没有中文索引」，而是实现把整句当作**连续短语**：问题里的空格、标点与措辞一旦和源文不连续，短语就匹配不到。逐级收缩实测仍为 0：

- `知识C 必须每天采一次，不然会永久丢数据？` → 0 行
- `为什么 knowledgeC 必须每天采一次，不然会永久丢数据？` → 0 行
- `knowledgeC 必须每天采一次` → 0 行

（该模式偶有非零返回字节，来自短语碰巧命中非目标块，故 hit 仍为 0。）

### 3.2 无索引基线（12 题平均）

| 指标 | 快照值 |
|---|---:|
| 每题扫描 | 37.79 MB |
| 每题命中文件 | 73.9 个 |
| 每题需阅读 | 5.67 MB |

| 每题耗时 | 0.101 s |

### 3.3 排序深度与追加实验

- 把候选放宽后重新定位：**12/12 题的目标块在任一模式 top-50 内**，说明问题在排序而非召回。
- 按文件聚合后重排，未改善 `kw` 与 `auto` 的 top-5 命中（仍 7/12 与 8/12）：简单把 chunk 换成文件级排序不够，需要证据评分、去重与多样性策略，而非单纯放大 top-k。

## 4. 三个可复核答案与出处

以下答案取自 gold 文件的 probe 行，路径相对仓库根目录，行号为本次快照的 1-based 行号。

### Q1：kc_snapshot 的保留策略是什么？

答案：近 14 天全量保留；更早的每个 ISO 周保留首份，并保留首份永久版本。出处：`temp/pending_decisions/DECISIONS_R347_kc_snapshot_scheduling.md:18`（该行同时给出稳态约 200 MB 上限的估算）。

### Q10：没有 TODO 时，反射器还会调用 LLM 吗？

答案：不会。`reflect/autonomous.py::check()` 先读 `temp/TODO.txt`；没有未完成项时返回 None，不调用 LLM，等效 0 token。出处：`memory/autonomous_operation_sop.md:11`。

### Q11：为什么 `agent start` 的参数不能写成 `--timeout-ms`？

答案：真机接口用的是 `--timeout`；写成 `--timeout-ms` 会触发 unknown option，导致补位失败。出处：`memory/global_mem_insight.txt:45`。
